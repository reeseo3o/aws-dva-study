## 1. ASG 개요

Auto Scaling Group(ASG)은 애플리케이션의 **부하 변화에 따라 EC2 인스턴스를 자동으로 추가하거나 제거**하여 최적의 성능과 비용 효율성을 제공하는 AWS 관리형 서비스입니다.

### 1.1. ASG의 주요 이점

- **자동 확장성**: 애플리케이션 부하에 따라 자동으로 인스턴스 수 조정
- **고가용성**: 여러 가용 영역에 인스턴스를 분산하여 장애 대응
- **비용 최적화**: 필요한 리소스만 사용하여 비용 절감
- **자동 복구**: 비정상 인스턴스를 자동으로 감지하고 교체
- **로드 밸런싱 통합**: ELB와 통합하여 트래픽 분산

### 1.2. ASG 핵심 구성 요소

- **그룹 크기 설정**: 최소, 최대, 원하는 용량 구성
- **시작 템플릿**: 인스턴스 생성을 위한 AMI, 인스턴스 유형 등 정의
- **스케일링 정책**: 스케일 인/아웃을 결정하는 조건 설정
- **상태 확인**: 인스턴스 상태 모니터링 및 자동 복구

## 2. 동작 방식

### 2.1. 기본 개념

ASG는 다음 세 가지 주요 용량 설정을 통해 운영됩니다.

- **최소 용량(Min Size)**: 항상 유지할 최소 인스턴스 수
  - 예: `Min=2`는 어떤 상황에서도 최소 2개의 인스턴스 유지
- **최대 용량(Max Size)**: 넘지 않아야 할 최대 인스턴스 수
  - 예: `Max=10`은 부하가 높아도 10개 이상의 인스턴스를 생성하지 않음
- **원하는 용량(Desired Capacity)**: 현재 유지하고자 하는 인스턴스 수
  - 예: `Desired=4`는 ASG가 4개의 활성 인스턴스 유지 시도

### 2.2. 스케일링 메커니즘

ASG는 다음 두 가지 주요 스케일링 방식을 지원합니다.

#### 2.2.1. 스케일 아웃 (Scale Out)

- 인스턴스 수를 **증가**시키는 과정
- 트래픽 증가, CPU 사용률 상승, 메모리 부족 등에 대응
- 예: CPU 사용률 70% 이상일 때 인스턴스 2개 추가

#### 2.2.2. 스케일 인 (Scale In)

- 인스턴스 수를 **감소**시키는 과정
- 자원 활용도가 낮을 때 비용 최적화를 위해 수행
- 예: CPU 사용률 30% 이하일 때 인스턴스 1개 종료

#### 2.2.3. 종료 정책 (Termination Policy)

ASG는 스케일 인 시 다음 기준에 따라 종료할 인스턴스를 선택합니다.

1. **기본 정책**: 가장 오래된 시작 구성/템플릿의 인스턴스 우선 종료
2. **가용 영역 밸런싱**: 인스턴스 수가 가장 많은 AZ에서 우선 종료
3. **온디맨드/스팟 인스턴스 밸런싱**: 온디맨드와 스팟 인스턴스 비율 유지

## 3. 시작 템플릿과 설정

### 3.1. 시작 템플릿 (Launch Template)

ASG에서 인스턴스를 생성하기 위한 **설정 정보**를 포함하는 구성입니다.

#### 3.1.1. 주요 구성 요소

- **AMI ID**: 사용할 OS와 소프트웨어 이미지
- **인스턴스 유형**: 컴퓨팅 리소스 크기 (t2.micro, m5.large 등)
- **키 페어**: SSH 접속을 위한 키 페어
- **보안 그룹**: 방화벽 규칙
- **IAM 역할**: 인스턴스의 AWS 권한
- **사용자 데이터(User Data)**: 시작 스크립트
- **네트워킹 설정**: 서브넷, IP 할당 방식
- **스토리지**: EBS 볼륨 구성

#### 3.1.2. 시작 템플릿 버전 관리

- 동일한 템플릿의 여러 버전 생성 및 관리 가능
- 버전 번호 또는 `$Latest`, `$Default` 지정 가능
- 롤백 및 점진적 배포 지원

### 3.2. 인스턴스 구매 옵션

ASG는 다양한 EC2 인스턴스 구매 옵션을 지원하여 비용 최적화를 제공합니다.

#### 3.2.1. 온디맨드 인스턴스

- 고정된 비용, 장기 약정 없음
- 안정적이고 예측 가능한 워크로드에 적합
- 가장 높은 가용성 제공

#### 3.2.2. 스팟 인스턴스

- 온디맨드 대비 최대 90% 할인 가능
- 중단 가능성 있음 (2분 알림 제공)
- 내결함성이 있는 워크로드에 적합 (배치 처리, 데이터 분석 등)

#### 3.2.3. 혼합 인스턴스 정책

- 온디맨드와 스팟 인스턴스의 조합 사용
- 비용 효율성과 안정성의 균형 유지
- 다양한 인스턴스 유형 사용 가능

## 4. 스케일링 정책과 전략

### 4.1. 동적 스케일링 (Dynamic Scaling)

실시간 메트릭에 따라 용량을 자동으로 조정하는 방식입니다.

#### 4.1.1. 대상 추적 스케일링 (Target Tracking)

- 특정 메트릭에 대해 목표값을 설정하고 이를 유지하도록 자동 조정
- 가장 간단하고 효과적인 방식
- 예: CPU 사용률 50% 유지, 각 인스턴스당 요청 수 1000개 유지

#### 4.1.2. 단계 스케일링 (Step Scaling)

- 경보 임계값에 따라 단계적으로 용량 조정
- 세밀한 제어 가능 (임계값마다 다른 조정 폭 설정)
- 예: CPU 70-80%일 때 +1, 80-90%일 때 +2, 90% 이상일 때 +3 인스턴스

#### 4.1.3. 단순 스케일링 (Simple Scaling)

- 단일 경보 임계값에 도달하면 지정된 만큼 용량 조정
- 조정 후 쿨다운 기간 필수
- 예: CPU 70% 이상일 때 인스턴스 2개 추가, 쿨다운 300초

### 4.2. 예측 스케일링 (Predictive Scaling)

- 과거 로드 패턴 분석을 통해 미래 용량 요구사항을 예측
- 일일, 주간, 계절적 패턴이 있는 워크로드에 효과적
- 사전에 용량을 확장하여 성능 저하 방지
- 기계 학습 기반으로 지속적으로 개선됨

### 4.3. 예약 스케일링 (Scheduled Scaling)

- 미리 정의된 시간에 용량을 조정
- 예측 가능한 로드 패턴에 적합
- 예: 업무 시간 시작 전 확장, 주말/휴일에 축소

```
# 예약 스케일링 예시
이름: Business-Hours-Scaling
반복: 월-금
시작 시간: 08:00 (UTC)
최소 용량: 8
최대 용량: 20
원하는 용량: 10

이름: After-Hours-Scaling
반복: 월-금
시작 시간: 18:00 (UTC)
최소 용량: 2
최대 용량: 10
원하는 용량: 4
```

### 4.4. 스케일링 기준 지표 (Metrics)

스케일링 결정의 기준이 되는 주요 지표들

| 지표                 | 설명                             | 일반적인 임계값   | 적합한 워크로드              |
| -------------------- | -------------------------------- | ----------------- | ---------------------------- |
| **CPU 사용률**       | 인스턴스의 CPU 사용 백분율       | 70-80%            | 컴퓨팅 집약적 작업           |
| **네트워크 인/아웃** | 인스턴스의 네트워크 트래픽       | 5-10 Gbps         | 콘텐츠 전송, 미디어 스트리밍 |
| **ELB 요청 수**      | 인스턴스당 로드 밸런서 요청 수   | 1000-5000 요청/분 | 웹 애플리케이션              |
| **SQS 대기열 길이**  | 처리 대기 중인 메시지 수         | 100-1000 메시지   | 이벤트 처리 시스템           |
| **메모리 사용률**    | RAM 사용 비율 (사용자 정의 지표) | 60-80%            | 메모리 집약적 애플리케이션   |
| **디스크 I/O**       | 디스크 읽기/쓰기 작업 수         | 250-500 IOPS      | 데이터베이스, 로그 처리      |

### 4.5. 쿨다운 기간 (Cooldown Period)

- 스케일링 활동 후 추가적인 스케일링을 일시 중지하는 시간
- 스케일링 활동 효과가 지표에 반영될 시간 확보
- 불필요한 스케일링 활동 방지
- 기본값: 300초(5분), 워크로드에 따라 조정 필요

## 5. 상태 확인과 인스턴스 수명 주기

### 5.1. 상태 확인 유형

ASG는 여러 종류의 상태 확인을 통해 인스턴스 상태를 모니터링합니다.

#### 5.1.1. EC2 상태 확인

- 하드웨어 및 소프트웨어 문제 감지
- 네트워크 연결성, 전원, 소프트웨어 오류 등 확인

#### 5.1.2. ELB 상태 확인

- 애플리케이션 레벨의 상태 확인
- HTTP/HTTPS 엔드포인트 응답 확인
- 애플리케이션 기능 정상 여부 검증

#### 5.1.3. 사용자 정의 상태 확인

- 애플리케이션 특성에 맞는 맞춤형 상태 확인
- CloudWatch 경보와 연동 가능
- 특정 조건 만족 시 비정상으로 판단

### 5.2. 인스턴스 수명 주기

ASG에서 인스턴스는 다음과 같은 수명 주기를 가집니다.

1. **Pending**: 인스턴스 시작 중
2. **Pending:Wait**: 수명 주기 훅 대기 중
3. **Pending:Proceed**: 수명 주기 훅 완료, 서비스로 진행 중
4. **InService**: 정상 작동 중
5. **Terminating**: 종료 중
6. **Terminating:Wait**: 종료 수명 주기 훅 대기 중
7. **Terminating:Proceed**: 종료 진행 중
8. **Terminated**: 종료 완료
9. **Detached**: ASG에서 분리됨
10. **Standby**: 일시적으로 서비스에서 제외됨

### 5.3. 수명 주기 훅 (Lifecycle Hooks)

수명 주기 훅을 사용하면 인스턴스의 시작/종료 과정에 사용자 정의 작업을 추가할 수 있습니다.

#### 5.3.1. 시작 수명 주기 훅

- 인스턴스가 서비스에 들어가기 전 실행
- 애플리케이션 설치, 구성, 데이터 로드 등에 활용
- 예: 소프트웨어 설치, 설정 파일 다운로드, 로그 시스템 연결

#### 5.3.2. 종료 수명 주기 훅

- 인스턴스가 종료되기 전 실행
- 데이터 백업, 안전한 종료 절차 등에 활용
- 예: 로그 업로드, 연결 종료, 상태 저장

```
# 수명 주기 훅 구성 예시
훅 이름: instance-launching-hook
ASG: my-web-app-asg
수명 주기 전환: Instance Launch
알림 대상: SNS 주제 또는 SQS 대기열
하트비트 타임아웃: 3600초 (최대 대기 시간)
기본 결과: ABANDON (타임아웃 시 인스턴스 폐기)
```

## 6. ASG 보안 및 네트워킹

### 6.1. IAM 역할 및 권한

ASG 작업을 위한 권한 설정

- **서비스 역할**: ASG가 다른 AWS 서비스와 상호 작용하기 위한 역할
- **인스턴스 프로필**: EC2 인스턴스에 부여되는 IAM 역할
- **최소 권한 원칙**: 필요한 권한만 부여하여 보안 강화

### 6.2. 네트워킹 구성

#### 6.2.1. VPC 및 서브넷 설정

- 여러 가용 영역의 서브넷에 인스턴스 분산 (권장: 최소 2개 이상의 AZ)
- 퍼블릭/프라이빗 서브넷 고려
- 퍼블릭 서브넷: 인터넷 접근 필요 시 (웹 서버)
- 프라이빗 서브넷: 내부 서비스용 (애플리케이션 서버, 데이터베이스)

#### 6.2.2. 보안 그룹 구성

- 인바운드/아웃바운드 트래픽 제어
- 필요한 포트만 개방 (최소 권한 원칙)
- 로드 밸런서와 연동 시 보안 그룹 연계 구성

```
# 웹 서버 보안 그룹 예시
인바운드:
  - 소스: ELB 보안 그룹, 포트: 80/443 (HTTP/HTTPS)
  - 소스: 관리 IP 범위, 포트: 22 (SSH)
아웃바운드:
  - 대상: 0.0.0.0/0, 포트: 443 (HTTPS)
  - 대상: 내부 서브넷, 포트: 3306 (MySQL)
```

## 7. 모니터링 및 로깅

### 7.1. CloudWatch 메트릭

ASG는 다음과 같은 주요 CloudWatch 메트릭을 제공합니다.

- **GroupMinSize**: 그룹의 최소 크기
- **GroupMaxSize**: 그룹의 최대 크기
- **GroupDesiredCapacity**: 그룹의 원하는 용량
- **GroupInServiceInstances**: 서비스 중인 인스턴스 수
- **GroupPendingInstances**: 대기 중인 인스턴스 수
- **GroupStandbyInstances**: 대기 상태의 인스턴스 수
- **GroupTerminatingInstances**: 종료 중인 인스턴스 수
- **GroupTotalInstances**: 총 인스턴스 수

### 7.2. CloudWatch 경보

메트릭 기반 경보를 설정하여 자동화 및 알림 구성

```
# CPU 사용률 경보 예시
경보 이름: high-cpu-usage
메트릭: CPUUtilization
통계: Average
기간: 5분
임계값: 80%
비교 연산자: >=
데이터포인트: 3 out of 3
작업: 스케일 아웃 정책 실행, SNS 알림 전송
```

### 7.3. CloudTrail 로깅

ASG API 호출을 기록하여 감사 및 문제 해결

- 누가, 언제, 어떤 API를 호출했는지 추적
- 보안 분석 및 규정 준수 감사에 활용
- 인시던트 발생 시 원인 분석에 활용

## 8. 실전 사용 사례

### 8.1. 웹 애플리케이션 (ELB + ASG)

```
# 아키텍처 구성
- 인터넷 → ALB → ASG(EC2 웹 서버) → RDS
- 지표: ALB 요청 수, CPU 사용률
- 스케일링 정책: 인스턴스당 요청 수 1000개 유지(대상 추적)
- 용량: Min=2, Max=10, Desired=4
- 다중 AZ 배포: 최소 3개 가용 영역
```

### 8.2. 배치 처리 워크로드

```
# 아키텍처 구성
- SQS 대기열 → ASG(스팟 인스턴스 중심) → S3/DynamoDB
- 지표: SQS 대기열 길이
- 스케일링 정책: 대기열 길이 기반 (100개 메시지당 1개 인스턴스)
- 용량: Min=0, Max=20, Desired=기반 계산
- 인스턴스 조합: 80% 스팟, 20% 온디맨드
```

### 8.3. 마이크로서비스 아키텍처

```
# 아키텍처 구성
- 각 마이크로서비스별 독립적인 ASG
- 서비스별 맞춤형 스케일링 정책
- 서비스 디스커버리: AWS App Mesh
- 로깅 및 모니터링: CloudWatch Container Insights
- 배포: ECS Fargate 또는 EKS
```

## 9. 모범 사례

### 9.1. 설계 원칙

- **다중 AZ 구성**: 최소 2개 이상의 가용 영역 사용
- **적절한 용량 설정**: 최소 용량은 2 이상으로 설정(고가용성)
- **인스턴스 유형 다양화**: 여러 인스턴스 패밀리 및 크기 활용
- **스팟/온디맨드 조합**: 비용과 안정성의 균형 고려

### 9.2. 성능 최적화

- **워밍업 시간 조정**: 애플리케이션 시작 특성에 맞게 설정
- **쿨다운 기간 최적화**: 스케일링 활동 간 적절한 간격 유지
- **점진적 스케일링**: 급격한 용량 변화보다 점진적 변화 선호
- **부하 테스트**: 스케일링 정책 효과 사전 검증

### 9.3. 비용 최적화

- **예측 스케일링 활용**: 사전에 용량 확보로 성능 유지
- **스팟 인스턴스 활용**: 내결함성이 있는 워크로드에 적합
- **자동 스케일 인**: 사용량 감소 시 리소스 회수
- **예약 인스턴스 고려**: 기본 용량에 예약 인스턴스 활용

### 9.4. 운영 안정성

- **점진적 배포**: 블루/그린 또는 롤링 배포 방식 활용
- **자동화된 상태 확인**: 애플리케이션 레벨 상태 확인 구현
- **수명 주기 훅 활용**: 정교한 시작/종료 프로세스 구현
- **백업 및 재해 복구**: 중요 데이터 백업 메커니즘 구현
