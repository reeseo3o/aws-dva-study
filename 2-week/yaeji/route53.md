# Route53 - AWS의 고가용성 DNS 서비스

## DNS(Domain Name System) 개요

DNS는 사람이 읽을 수 있는 도메인 이름(예: www.google.com)을 컴퓨터가 이해할 수 있는 IP 주소(예: 192.168.1.1)로 변환하는 시스템입니다. 인터넷의 핵심 기능으로, 웹 브라우저가 웹 서버를 찾아 통신할 수 있게 해줍니다.

## DNS 주요 용어

| 용어 | 설명 | 예시 |
|------|------|------|
| **도메인 레지스트라** | 도메인 이름을 등록하는 기관 | Amazon Route 53, GoDaddy |
| **DNS 레코드** | 도메인 이름과 IP 주소를 연결하는 설정 | A, AAAA, CNAME, NS 등 |
| **존 파일** | 모든 DNS 레코드를 포함하는 파일 | - |
| **이름 서버** | DNS 쿼리를 실제로 해결하는 서버 | - |
| **TLD** | 최상위 도메인, 도메인 이름의 마지막 부분 | .com, .org, .net |
| **SLD** | 2단계 도메인, TLD 앞의 부분 | amazon.com의 'amazon' |
| **FQDN** | 전체 주소 도메인 이름 | api.www.example.com. |

## DNS 구조 계층

```
                     .(루트)
                       |
         +-------------+-------------+
         |             |             |
       .com          .org          .net (TLD)
         |             |             |
   +-----------+  +-----------+  +-----------+
   |           |  |           |  |           |
example.com  google.com    amazon.com      ... (SLD)
   |
+-------+-------+
|       |       |
www    api    mail (서브도메인)
```

## DNS 작동 방식

1. 사용자: 브라우저에 `example.com` 입력
2. 로컬 DNS 서버: "example.com의 IP 주소는?"
3. 루트 DNS 서버: ".com DNS 서버의 주소는 여기"
4. 로컬 DNS → .com TLD 서버: "example.com의 IP 주소는?"
5. .com TLD 서버: "example.com 네임서버의 주소는 여기"
6. 로컬 DNS → example.com 네임서버: "example.com의 IP 주소는?"
7. example.com 네임서버: "IP 주소는 93.184.216.34"
8. 로컬 DNS: 결과 캐싱 및 브라우저에 전달
9. 브라우저: 해당 IP 주소로 직접 연결

## Route53 소개

Route53은 AWS의 완전 관리형 DNS 서비스입니다. "53"은 DNS가 사용하는 포트 번호(53)에서 유래했습니다.

### 주요 특징
- ✅ 고가용성과 확장성 보장
- ✅ 완전 관리형 서비스 (인프라 관리 불필요)
- ✅ 권한 있는 DNS (사용자가 직접 DNS 레코드 업데이트 가능)
- ✅ 도메인 등록 서비스 제공
- ✅ 리소스 상태 확인 기능
- ✅ AWS에서 유일하게 100% SLA 제공 서비스

## DNS 레코드 유형

### A 레코드 (Address)
- **역할**: 도메인 이름 → IPv4 주소 매핑
- **예시**: `example.com → 192.168.1.1`

### AAAA 레코드
- **역할**: 도메인 이름 → IPv6 주소 매핑
- **예시**: `example.com → 2001:0db8:85a3:0000:0000:8a2e:0370:7334`

### CNAME 레코드 (Canonical Name)
- **역할**: 호스트 이름 → 다른 호스트 이름 매핑
- **제한**: 루트 도메인(Zone Apex)에는 사용 불가
- **예시**: `www.example.com → example.com`

### NS 레코드 (Name Server)
- **역할**: 호스팅 존의 권한 있는 이름 서버 지정
- **기능**: 도메인에 대한 DNS 쿼리를 처리할 서버 정의

## 호스팅 존(Hosting Zone)

호스팅 존은 도메인과 서브도메인으로 가는 트래픽 라우팅 방식을 정의하는 레코드의 컨테이너입니다.

### 퍼블릭 호스팅 존
- **용도**: 인터넷에서 공개적으로 접근 가능한 도메인 관리
- **예시**: example.com에 대한 DNS 쿼리 응답

### 프라이빗 호스팅 존
- **용도**: 특정 VPC 내에서만 접근 가능한 도메인 관리
- **예시**: webapp.example.internal, api.example.internal

## TTL (Time To Live)

TTL은 DNS 레코드가 DNS 리졸버에 캐싱되는 시간을 초 단위로 지정합니다.

### 높은 TTL (예: 24시간)
- ✅ Route53 트래픽 감소, 비용 절감
- ❌ 레코드 변경 시 전파 시간이 오래 걸림

### 낮은 TTL (예: 60초)
- ✅ 레코드 변경이 빠르게 전파됨
- ❌ Route53 트래픽 증가, 비용 증가

## CNAME vs Alias 레코드

### CNAME
- **기능**: 호스트 이름을 다른 호스트 이름으로 매핑
- **제한**: 루트 도메인(example.com)에는 사용 불가
- **사용**: 서브도메인(www.example.com)에만 사용 가능

### Alias 레코드
- **기능**: Route53 전용 기능으로 호스트 이름을 AWS 리소스로 매핑
- **장점**: 
  - 루트 도메인 및 서브도메인 모두에 사용 가능
  - 무료로 사용 가능
  - 자체적으로 상태 확인 가능
  - TTL 설정 불필요 (자동 관리)

### Alias 레코드 대상
- ELB (Elastic Load Balancer)
- CloudFront 배포
- API Gateway
- Elastic Beanstalk 환경
- S3 웹사이트
- VPC 인터페이스 엔드포인트
- Global Accelerator 가속기
- Route53 레코드

> **중요**: EC2 인스턴스의 DNS 이름에는 Alias 레코드를 설정할 수 없음

## 라우팅 정책

Route53은 다양한 라우팅 정책을 제공하여 DNS 쿼리에 응답하는 방식을 제어합니다.

### 1. 단순 라우팅 정책 (Simple)
- **기능**: 트래픽을 단일 리소스로 라우팅
- **특징**: 
  - 동일한 레코드에 여러 값 지정 가능 (클라이언트가 무작위로 선택)
  - 상태 확인과 연결 불가

### 2. 가중치 기반 라우팅 정책 (Weighted)
- **기능**: 각 리소스에 상대적 가중치를 할당
- **특징**: 트래픽이 가중치 비율에 따라 분산
- **사용 사례**: 
  - 지역 간 로드 밸런싱
  - 새 애플리케이션 테스트 (카나리 배포)
- **규칙**:
  - 가중치가 0이면 트래픽 중단
  - 모든 가중치가 0이면 동일한 가중치로 처리

### 3. 지연 시간 기반 라우팅 정책 (Latency)
- **기능**: 지연 시간이 가장 짧은 리소스로 라우팅
- **특징**:
  - AWS 리전 간의 지연 시간 측정 기반
  - 사용자가 가장 가까운 AWS 리전으로 라우팅됨
- **적합**: 지연 시간에 민감한 애플리케이션에 적합

### 4. 장애 조치 라우팅 정책 (Failover)
- **기능**: 기본 리소스와 보조 리소스 설정
- **특징**:
  - 기본 리소스에 상태 확인 필수
  - 기본 리소스가 비정상이면 보조 리소스로 자동 전환
- **적합**: 재해 복구 시나리오

### 5. 지리적 라우팅 정책 (Geolocation)
- **기능**: 사용자의 지리적 위치에 따라 라우팅
- **특징**:
  - 대륙, 국가, 미국의 경우 주 단위로 설정 가능
  - 기본 레코드는 일치하는 위치가 없는 경우 필요
- **사용 사례**: 콘텐츠 현지화, 트래픽 제한

### 6. 지리 근접 라우팅 정책 (Geoproximity)
- **기능**: 리소스와 사용자 간의 지리적 근접성 기반 라우팅
- **특징**:
  - 편향(bias) 값으로 영향 범위 조정 가능
    - 양수: 리소스 영향 범위 확장
    - 음수: 리소스 영향 범위 축소
  - 리소스는 AWS 리전 또는 위도/경도로 지정
- **요구 사항**: Route53 Traffic Flow 필요

### 7. IP 기반 라우팅 정책 (IP-based)
- **기능**: 클라이언트 IP CIDR 범위에 따라 라우팅
- **사용 사례**: 
  - 특정 ISP 또는 지역을 특정 엔드포인트로 라우팅
  - 네트워크 성능 최적화 및 비용 절감

### 8. 다중값 응답 라우팅 정책 (Multi-value Answer)
- **기능**: 트래픽을 여러 리소스로 분산
- **특징**:
  - 최대 8개의 정상 레코드 반환
  - 상태 확인과 연결 가능
  - 클라이언트 측 로드 밸런싱 제공
- **주의**: ELB를 대체하지는 않음

## 상태 확인

Route53은 리소스의 상태를 모니터링하고 비정상 리소스로 트래픽이 라우팅되지 않도록 합니다.

### 1. 엔드포인트 상태 확인
- **대상**: 공용 엔드포인트 모니터링 (웹 서버, API 등)
- **방식**:
  - 전 세계에서 약 15개의 상태 확인 요청
  - 18% 이상의 상태 확인이 정상이면 '정상' 간주
- **설정**:
  - 확인 간격: 30초(표준) 또는 10초(빠른 확인, 추가 비용)
  - 프로토콜: HTTP, HTTPS, TCP 지원
- **성공 기준**:
  - 2xx 또는 3xx 응답 코드가 '정상' 간주
  - 응답 본문에서 특정 문자열 검색 가능 (처음 5,120바이트)

### 2. 계산된 상태 확인
- **기능**: 여러 상태 확인 결과를 하나로 통합
- **특징**:
  - 논리 연산자 사용: AND, OR, NOT
  - 최대 256개의 하위 상태 확인 모니터링 가능
  - 통과에 필요한 상태 확인 수 지정 가능

### 3. 프라이빗 리소스 상태 확인
- **대상**: VPC 내 프라이빗 리소스 모니터링
- **방식**: CloudWatch 메트릭 + CloudWatch 경보 사용
- **판단**: 경보가 ALARM 상태가 되면 상태 확인이 비정상으로 간주

## Traffic Flow

- **기능**: 복잡한 라우팅 결정 트리 관리를 위한 시각적 편집기
- **장점**:
  - 여러 라우팅 정책 조합 가능
  - 정책 버전 관리 지원
  - 호스팅 존에 쉽게 적용 가능

## 타사 도메인 & Route53

도메인 이름 레지스트라와 DNS 서비스는 별개로 사용 가능합니다:

1. 타사 레지스트라(예: GoDaddy)에서 도메인 구매
2. Route53에서 해당 도메인의 공용 호스팅 존 생성
3. 레지스트라에서 네임서버를 Route53의 네임서버로 변경
4. Route53 콘솔에서 DNS 레코드 관리

이렇게 하면 도메인 등록은 타사를 통해 유지하면서 Route53의 고급 DNS 기능을 활용할 수 있습니다.
