## 1. ELB 개요

AWS Elastic Load Balancer(ELB)는 들어오는 애플리케이션 트래픽을 여러 대상(EC2 인스턴스, 컨테이너, IP 주소 등)에 자동으로 분산시키는 관리형 서비스입니다. ELB는 단일 액세스 포인트를 통해 애플리케이션의 가용성과 확장성을 보장합니다.

### 1.1. ELB의 주요 이점

- **트래픽 분산**: 여러 리소스에 부하를 균등하게 분산
- **자동 확장**: 트래픽 변화에 따라 자동으로 확장
- **장애 탐지**: 비정상 리소스를 감지하고 트래픽 재라우팅
- **보안 강화**: SSL/TLS 암호화 및 보안 기능 제공
- **운영 간소화**: 관리형 서비스로 유지보수 최소화

## 2. 고가용성과 확장성

### 2.1. 고가용성 (High Availability)

ELB는 여러 가용 영역(AZ, Availability Zone)에 걸쳐 자동으로 배포되어 단일 장애 지점을 제거합니다. 이를 통해

- 하나의 AZ에 장애가 발생해도 서비스 중단 없음
- 데이터 센터 수준의 장애에도 지속적인 서비스 제공
- 정기적인 상태 확인을 통해 비정상 인스턴스로의 트래픽 차단

> **모범 사례**: 최소 두 개 이상의 가용 영역에 리소스를 배포하여 고가용성 확보

### 2.2. 확장성 (Scalability)

ELB는 두 가지 주요 확장 방식을 지원합니다.

#### 2.2.1. 수직 확장 (Vertical Scaling)

- 개별 **인스턴스의 크기(CPU, 메모리 등)를 확장**하는 방식
- 주로 **데이터베이스(RDS, ElastiCache)** 같은 분산되지 않은 시스템에 적합
- 예: t2.micro → t2.large → r5.2xlarge로 업그레이드
- **한계**: 하드웨어 제한으로 무한 확장 불가능

#### 2.2.2. 수평 확장 (Horizontal Scaling)

- **인스턴스 개수를 늘리는 방식**으로 트래픽 분산
- Auto Scaling Group과 ELB 조합으로 자동화 가능
- 분산 시스템에 이상적(웹 서버, 마이크로서비스 등)
- **장점**: 거의 무제한 확장 가능

## 3. EC2에서의 확장

- **수직 확장:** 스케일 업/다운 (t2.nano에서 u-12tb까지 확장 가능)
- **수평 확장:** 스케일 아웃/인 (Auto Scaling Group 및 ELB 활용)
- 다중 AZ 환경에서 고가용성 제공

## 3. AWS 로드 밸런서 유형 비교

AWS는 네 가지 유형의 관리형 로드 밸런서를 제공합니다.

### 3.1. 로드 밸런서 유형 비교표

| 특성            | 애플리케이션 로드 밸런서 (ALB)  | 네트워크 로드 밸런서 (NLB) | 게이트웨이 로드 밸런서 (GWLB) | 클래식 로드 밸런서 (CLB) |
| --------------- | ------------------------------- | -------------------------- | ----------------------------- | ------------------------ |
| **OSI 계층**    | 7계층 (애플리케이션)            | 4계층 (전송)               | 3/4계층 (네트워크)            | 4/7계층 (혼합)           |
| **프로토콜**    | HTTP, HTTPS, gRPC               | TCP, UDP, TLS              | IP 기반                       | HTTP, HTTPS, TCP, SSL    |
| **라우팅 방식** | 콘텐츠 기반(경로, 호스트, 헤더) | IP 기반, 포트 기반         | IP 패킷 전달                  | 기본 라우팅              |
| **대상 유형**   | EC2, IP, Lambda, 컨테이너       | EC2, IP, ALB               | EC2, IP                       | EC2 인스턴스             |
| **알고리즘**    | 라운드 로빈                     | 흐름 해시                  | 라우팅 테이블                 | 라운드 로빈/최소 연결    |
| **지연 시간**   | 낮음                            | 매우 낮음                  | 낮음                          | 중간                     |
| **정적 IP**     | 지원 안 함                      | 지원                       | 지원                          | 지원 안 함               |
| **주요 용도**   | 웹 애플리케이션, 마이크로서비스 | 고성능 TCP/UDP 앱, 게임    | 보안 어플라이언스             | 레거시 애플리케이션      |

### 3.2. 애플리케이션 로드 밸런서 (ALB)

- **OSI 7계층(애플리케이션 계층)** 작동
- **경로 기반 라우팅**: URL 경로별로 다른 대상 그룹으로 요청 라우팅 가능
  예: `/api/*` → API 서버, `/images/*` → 이미지 서버
- **호스트 기반 라우팅**: 도메인 이름에 따라 라우팅
  예: `api.example.com` → API 서버, `www.example.com` → 웹 서버
- **HTTP 헤더 기반 라우팅**: 헤더, 쿠키, 쿼리 문자열 등으로 라우팅
- **마이크로서비스 및 컨테이너**에 최적화됨
- **WebSocket 및 HTTP/2** 지원

### 3.3. 네트워크 로드 밸런서 (NLB)

- **OSI 4계층(전송 계층)** 작동
- **초고성능 및 최저 지연 시간** 제공
- **고정 IP 지원**: 각 가용 영역마다 고정 IP 제공
- TCP, UDP, TLS 트래픽 처리에 최적화
- 초당 수백만 요청 처리 가능
- 연결 유지(connection persistence) 지원
- 갑작스런 트래픽 급증에 빠르게 대응 가능

### 3.4. 게이트웨이 로드 밸런서 (GWLB)

- **OSI 3/4계층(네트워크/전송 계층)** 작동
- **보안 어플라이언스** 배포와 확장에 특화
  - 방화벽
  - 침입 탐지/방지 시스템
  - 딥 패킷 인스펙션
- **투명한 네트워크 게이트웨이** 역할
- 단일 진입/진출 지점을 제공하여 모든 트래픽 검사 가능
- 가상 어플라이언스의 수평적 확장 지원

### 3.5. 클래식 로드 밸런서 (CLB)

- 2009년 출시된 **1세대 로드 밸런서**
- 4/7계층 기능 혼합
- **레거시 애플리케이션**에 사용
- 현재 AWS에서는 사용을 권장하지 않음
- 신규 구축시 ALB나 NLB 사용 권장

## 4. ELB 핵심 기능

### 4.1. Health Check (상태 확인)

ELB는 등록된 대상의 상태를 주기적으로 확인하여 정상적인 대상으로만 트래픽을 라우팅합니다.

- **프로토콜**: HTTP, HTTPS, TCP 등
- **경로**: 주로 `/health` 같은 전용 엔드포인트 사용
- **주기**: 확인 간격, 타임아웃, 임계값 설정 가능
- **동작**: 비정상 대상 감지 시 자동으로 트래픽 우회

```
# 상태 확인 설정 예시
프로토콜: HTTP
포트: 80
경로: /health
간격: 30초
임계값: 2회 (2회 연속 실패 시 비정상으로 판단)
타임아웃: 5초
```

### 4.2. Sticky Sessions (세션 어피니티)

특정 클라이언트의 모든 요청이 동일한 대상 인스턴스로 라우팅되도록 보장합니다.

- **사용 사례**: 사용자 로그인 상태, 장바구니 정보 유지 필요 시
- **쿠키 기반 작동**:
  1. **애플리케이션 쿠키**: 애플리케이션에서 생성하고 ELB가 추적
  2. **지속 시간 쿠키**: ELB가 자동 생성하고 관리 (AWSELB)
- **주의점**: 불균형한 부하 분산 가능성

### 4.3. Cross-Zone Load Balancing (교차 영역 로드 밸런싱)

여러 가용 영역에 걸쳐 트래픽을 균등하게 분산하는 기능입니다:

#### 활성화된 경우:

- 각 로드 밸런서 노드가 **모든 가용 영역의 모든 대상**으로 트래픽 분산
- 예: AZ1에 2개, AZ2에 8개의 인스턴스가 있을 때, 각 인스턴스는 전체 트래픽의 10%씩 수신

#### 비활성화된 경우

- 각 로드 밸런서 노드가 **해당 가용 영역 내의 대상**으로만 트래픽 분산
- 예: AZ1의 각 인스턴스는 25%, AZ2의 각 인스턴스는 6.25%의 트래픽 수신

#### 기본 설정

- **ALB, CLB**: 기본 활성화 (무료)
- **NLB, GWLB**: 기본 비활성화 (활성화 시 추가 비용)

## 5. ELB 보안 및 네트워킹

### 5.1. 보안 그룹 설정

ELB와 대상 인스턴스의 보안을 위한 권장 설정

- **ELB 보안 그룹**

  - 인바운드: 클라이언트의 HTTP(80)/HTTPS(443) 트래픽 허용
  - 아웃바운드: 대상 인스턴스의 애플리케이션 포트로의 트래픽 허용

- **EC2 인스턴스 보안 그룹**
  - 인바운드: ELB 보안 그룹에서 오는 트래픽만 허용
  - 아웃바운드: 필요한 외부 연결만 허용

```
# ELB 보안 그룹 예시
인바운드: 0.0.0.0/0에서 포트 80, 443 허용
아웃바운드: 대상 인스턴스 보안 그룹으로 포트 8080 허용

# EC2 보안 그룹 예시
인바운드: ELB 보안 그룹에서 포트 8080 허용
아웃바운드: 모든 트래픽 허용
```

### 5.2. SSL/TLS 인증

ELB는 클라이언트와의 보안 통신 및 인증서 관리를 지원합니다.

- **SSL 종료(SSL Termination)**: ELB에서 HTTPS 연결 종료 후 HTTP로 백엔드 통신
- **ACM 통합**: AWS Certificate Manager를 통한 인증서 관리
- **SNI 지원**: Server Name Indication으로 여러 도메인 지원
  - ALB, NLB: 다중 인증서 지원
  - CLB: 단일 인증서만 지원
- **보안 정책**: 다양한 보안 프로토콜 및 암호화 수준 설정 가능

### 5.3. 연결 드레이닝 (Connection Draining)

인스턴스가 등록 해제되거나 비정상 상태가 될 때 기존 연결을 안전하게 완료하는 기능

- **매커니즘**
  1. 인스턴스가 등록 해제 시작
  2. 새 연결 차단, 기존 연결은 유지
  3. 타임아웃 후 남은 연결 강제 종료
- **타임아웃 설정**: 1-3600초 (기본값: 300초)
- **최적화 전략**:
  - 짧은 연결: 낮은 타임아웃 값
  - 긴 연결: 높은 타임아웃 값

## 6. 실전 사용 사례

### 6.1. 웹 애플리케이션 (ALB 활용)

```
# 아키텍처 구성
- 인터넷 → ALB(HTTPS) → EC2 웹 서버(HTTP)
- 경로 기반 라우팅:
  • /api/* → API 서버 대상 그룹
  • /images/* → 정적 콘텐츠 서버 대상 그룹
  • /* → 기본 웹 서버 대상 그룹
```

### 6.2. 고성능 게임 서버 (NLB 활용)

```
# 아키텍처 구성
- 게임 클라이언트 → NLB(UDP/TCP) → 게임 서버
- 특징:
  • 고정 IP로 변경 없는 연결 주소 제공
  • 초저지연 트래픽 라우팅
  • 갑작스런 사용자 급증에도 안정적 성능
```

### 6.3. 보안 인프라 (GWLB 활용)

```
# 아키텍처 구성
- 인터넷 트래픽 → GWLB → 보안 어플라이언스(방화벽/IDS/IPS) → ALB → 애플리케이션
- 특징:
  • 모든 트래픽을 단일 진입점으로 통합
  • 보안 검사를 위한 인라인 트래픽 검사
  • 보안 어플라이언스 수평 확장 지원
```

## 7. 모범 사례

### 7.1. 아키텍처 설계

- **다중 AZ 배포**: 최소 2개 이상의 가용 영역 활용
- **적절한 로드 밸런서 선택**:
  - 웹 애플리케이션 → ALB
  - 고성능/저지연 요구사항 → NLB
  - 보안 어플라이언스 필요 → GWLB
- **Auto Scaling과 통합**: 자동 확장 구성으로 탄력성 확보

### 7.2. 성능 최적화

- **적절한 인스턴스 크기와 수**: 워크로드에 맞는 용량 계획
- **교차 영역 로드 밸런싱 활성화**: 균등한 부하 분산 보장
- **적절한 타임아웃 설정**: 애플리케이션 특성에 맞게 조정

### 7.3. 모니터링 및 로깅

- **CloudWatch 지표 활용**: 핵심 지표 모니터링 및 경보 설정
  - RequestCount, TargetResponseTime, HTTPCode_ELB_5XX 등
- **액세스 로그 활성화**: 트래픽 분석 및 문제 해결
- **Health Check 최적화**: 애플리케이션에 맞는 상태 확인 경로 및 간격 설정

### 7.4. 보안 강화

- **HTTPS만 사용**: 모든 트래픽 암호화
- **보안 그룹 최소 권한 원칙 적용**: 필요한 포트만 개방
- **최신 보안 정책 사용**: 강력한 암호화 알고리즘 적용
- **WAF 통합**: 애플리케이션 레이어 공격 방어 (ALB와 통합)
