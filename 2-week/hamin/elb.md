# ELB

Elastic Load Balancing(ELB)은 하나 이상의 가용 영역(AZ)에 있는 여러 대상 및 가상 어플라이언스에서 들어오는 애플리케이션 트래픽을 자동으로 분산합니다.

로드밸런서 자체의 역할을 쉽게 이해하자면 프록시 서버라고 생각하면 될 거 같습니다.

프록시 서버의 역할이 보통 클라이언트와 서버 사이에서 데이터를 전달해주는 역할을 하는데 로드밸런서가 딱 이런 역할을 합니다.

즉 로드밸런서도 별도의 네트워크 서버이며 중간에서
- 부하를 분산해주거나
- SSL을 암복호화 해서 전달하거나
- 부하의 대상이 되는 인스턴스들의 헬스체크를 담당하는 등의 역할을 합니다.

잠깐 프록시 서버에 대한 이야기를 조금만 더 해보겠습니다.

프록시 서버는 Forward Proxy와 Reverse Proxy가 있는데

Reverse Proxy의 경우 프록시 서버를 통해 최종적으로 요청을 받는 서버의 정보가 감춰져 있습니다. 즉 클라이언트의 경우 요청의 대상이 되는 엔드포인트 서버가 이 프록시 서버가 되며 이 프록시 서버를 통해 실제 내 요청이 어느 서버로 가는지는 알 수 없습니다.

그런 면에서 로드밸런서는 이 Reverse Proxy와 매우 유사합니다. (Forward Proxy는 설명 안함 대충 리버스의 리버스겠쥬?)

로드밸런서의 경우에도 요청하는 클라이언트의 경우 엔드포인트가 이 로드밸런서의 dns입니다. 실제 이 dns가 이 요청을 수행하기 위해 하위의 어떤 인스턴스에게 요청을 보내는지 알 수 없습니다.

## 로드밸런서 종류

AWS에서 제공하는 로드밸런서는
L7에 속하는 Application Load Balancer가 있고
L4에 속하는 Network Load Balancer
L4~L3에 속하는 Gateway Load Balancer가 있습니다.

### ALB (Application Load Balancer)
- OSI 7계층중 7계층에 해당하는 Application Layer에서 부하를 분산하는 로드 밸런서입니다.
- Application Layer에 위치하기 때문에 HTTP, HTTPS 내용을 바탕으로 부하를 분산할 수 있습니다. (HTTP 헤더 값을 보고 판단)
- SSL 인증서를 탑재할 수 있어 대상 그룹인 EC2 인스턴스를 대신하여 SSL을 복호화 할 수 있습니다.(복호화를 위한 별도의 추가 설정이 필요하지 않습니다. ec2 단에서 직접 복호화를 구현하지 않아도 되니 매우 편리합니다)

### NLB (Network Load Balancer)
- OSI 7계층중 4계층에 해당하는 Transport Layer에서 부하를 분산하는 로드 밸런서입니다.
- TCP, UDP를 사용하여 부하를 분산하므로, HTTP 헤더를 해석하지못해 HTTP 헤더를 기반으로 부하를 분산할 순 없습니다. 
- 4계층에 속해있기 때문에 6계층 수준인 암호화된 SSL 데이터를 이해할 수 없습니다.(복호화가 안된다는 이야기 때문에 인스턴스에서 직접 복호화 진행해야 함 다만 필요에 의해 여러 ALB를 두고 그 상위에 NLB를 두는 경우가 있음)
- 다만 7계층까지 가지 않고 4계층 수준에서 라우팅이 진행되기에 속도가 ALB에 빠릅니다.

### GLB (Gateway Load Balancer)
- OSI 계층중 3계층에 해당하는 Network Layer에서 부하를 분산하는 로드 밸런서입니다.

## ELB의 구성요소

### 로드밸런서
설명 했음

### 리스너
클라이언트의 요청을 대상 그룹으로 라우팅 하는 역할

### 타겟 그룹
실제 요청을 처리하는 분산 대상들의 집합


## ALB의 역할

SSL의 암복호화와 헬스 체크, 스티키 세션의 역할을 해줍니다.

SSL 암복호화는 앞에 설명했으며, 헬스 체크의 경우 타겟 그룹에 대한 헬스체크를 진행하여 정상이 아니라고 판단되면 해당 트래픽을 보내지 않습니다.

스티키 세션은
- 클라이언트와 서버간의 맵핑을 기억한 후 해당 클라이언트의 요청을 모두 동일한 서버로만 보내 세션을 유지하는 방식입니다.

로컬 세션이 필요한 애플리케이션을 비교적 간단히 확장하고자 할 때 자주 쓰이는 방법으로 보통 실제 운영에서는
세션 기반 방식을 사용할 때는 세션 정보를 서버가 저장하고 있거나 아니면 아예 jwt 방식의 인증을 사용하기에 스티키 세션 자체가 그렇게 쓸모있나 싶긴 합니다.

매 요청마다 동일한 세션을 보장해야 하는 경우라면 결국 서버가 스케일 아웃된 상태라는 뜻입니다.
이때 로드밸런서를 사용하는 이유는 스케일 아웃된 서버로 트래픽을 적절하게 분산하는게 목적입니다. 그런데 스티키 세션을 사용하면 특정 트래픽이 고정된 서버만을 향하므로 효율적인 분산을 유지하기 어렵습니다.

## 교차영역 로드밸런싱
이런 경우가 있을 수 있습니다.
AZ별로 트래픽 분산 비율을 적절히 나눠놨지만 각 AZ별 실제 보유한 인스턴스 수가 다르다면?
어떤 AZ는 50%의 트래픽을 2개의 인스턴스로 감당하고 어떤 AZ는 50%의 트래픽을 4개로 감당하게 될 수 있습니다.

이때 활용하는 기능이 교차영역 로드밸런싱입니다.

이 기능을 활성화하면 각 AZ별 로드밸런서 노드가 서로 다른 AZ를 넘나들며 모든 인스턴스들이 동일한 트래픽을 분배받도록 해줍니다.

### 로드밸런서의 DNS
우린 1개의 로드밸런서를 생성했지만 실제로는 각 가용영역별로 로드밸런서 노드가 생성될 수 있습니다.
이는 시스템의 고가용성을 위함입니다.

즉 실제 대상이 되는 로드밸런서 노드가 n개 입니다.

로드밸런서를 생성해보셨다면 별도의 IP를 확인할 수 없다는 점을 알 수 있습니다.

즉 1개의 IP가 아니기에 이 노드들의 IP를 묶어 DNS로 반환하고 있으며, 클라이언트가 이 DNS를 조회할 때(요청 과정에서) AWS 내부의 서버가 적절한 노드의 IP를 반환하는 방식입니다.

## 그 외

### ALB & NLB에서 하나의 리스너에 여러 SSL 인증서를 로드하는 기능
AWS의 Application Load Balancer(ALB) 및 Network Load Balancer(NLB)에서는 SNI(Server Name Indication) 기능을 활용하여 하나의 리스너에 여러 개의 SSL 인증서를 로드할 수 있습니다.

### SNI(Server Name Indication)란?
- SNI(Server Name Indication)는 TLS 확장 기능중 하나로, 클라이언트가 접속 시 요청하는 도메인 이름을 서버에 전달하여 해당 도메인에 맞는 SSL 인증서를 제공하는 방식입니다.

즉, 하나의 로드 밸런서(리스너)에 여러 개의 SSL 인증서를 설정할 수 있으며, 도메인에 맞는 올바른 인증서를 선택하여 TLS 핸드셰이크를 수행할 수 있습니다.

- ALB (Application Load Balancer): SNI를 지원하며, 여러 도메인에 대해 각기 다른 SSL 인증서를 설정할 수 있음.
- NLB (Network Load Balancer): TLS 리스너에서 SNI를 지원하여 다중 인증서 설정 가능.
