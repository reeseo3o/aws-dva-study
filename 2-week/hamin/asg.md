# ASG (Auto Scaling Group)

Auto Scaling Group은 트래픽 증가에 따라 인스턴스를 자동으로 늘리고, 트래픽 감소 시 불필요한 인스턴스를 줄여주는 AWS의 관리형 서비스입니다.

## 기본 목표
- 필요할 때 자동으로 인스턴스를 추가(Scale-out)
- 불필요한 인스턴스는 자동으로 제거(Scale-in)
- 특정 최소(Minimum), 최대(Maximum) 인스턴스 개수를 설정 가능
- ELB와 연동하여 부하 분산 가능
- 비정상 인스턴스 감지 및 교체

특징으로는 ASG 자체는 무료입니다. (사용하는 EC2 비용만 부과. 다만 전략을 잘못 세워서 불필요한 scale-out이 생기면 지갑 얇아짐)

## ASG와 로드 밸런서(ELB) 연동
ASG는 ELB와 연결할 수 있으며, 이를 통해 트래픽을 자동으로 균형 있게 분산합니다.

- SG에 포함된 모든 인스턴스는 ELB에 자동으로 등록됩니다.
- ELB의 헬스 체크를 통과한 인스턴스만 트래픽을 받음
- 만약 특정 인스턴스가 비정상으로 판정되면, ASG가 새로운 인스턴스를 생성하여 교체

이때 ELB의 헬스 체크와 ASG의 헬스 체크가 다르다는 것을 알 수 있습니다.

ELB에서의 헬스체크는 통과하지 못했을 경우 단순 트래픽을 전달하지 않는 수준으로 대응합니다.
ASG의 경우 헬스체크에 통과하지 못하면 해당 인스턴스를 종료하고 교체합니다.

즉 여기서의 연동이란 ELB 수준에서 통과하지 못하고 트래픽이 전달 안되었을 경우 그 결과를 반영하여 ASG가 인스턴스를 종료하고 교체하는 과정을 말합니다.

그냥 해주는건 아니고 연동을 직접 해줘야 합니다(어렵진 않은듯)

## 스케일링 정책(Scaling Policies)
ASG는 트래픽 상황에 맞춰 스케일링 정책을 자동으로 적용합니다.
대표적인 스케일링 방식은 다음과 같습니다.

1. 동적 스케일링 (Dynamic Scaling)
특정 CPU 사용률, 네트워크 트래픽 등 지표를 기준으로 스케일링이 자동으로 발생
예) CPU 사용률이 70% 이상이면 새로운 인스턴스를 추가하고, 30% 미만이면 축소

2. 단순 스케일링 (Simple Scaling)
CloudWatch 알람을 설정하여 특정 조건을 충족하면 즉시 인스턴스를 추가/삭제
예) CPU 사용률이 80% 이상이면 즉시 2개 추가, 20% 이하이면 1개 제거

3. 예약 스케일링 (Scheduled Scaling)
특정 시간대에 인스턴스를 미리 늘리거나 줄임
예) 평일 오전 9시~오후 6시 사이에는 인스턴스 5개, 나머지 시간에는 2개 유지

4. 예측 스케일링 (Predictive Scaling)
과거 트래픽 패턴을 학습하여 미리 스케일링을 적용
예) 매주 월요일 오전 9시에 트래픽이 증가하는 패턴이 있다면, 사전에 인스턴스를 늘려 놓음

## 스케일링 주요 지표 (Scaling Metrics)

위의 정책을 잘 선택하고 활용하기 위해선 기준이 되는 지표가 중요하겠죠?

대표적인 지표를 살펴봅시다.

1. CPU 사용률 (CPU Utilization)
현재 생성된 인스턴스들의 CPU 사용률이 일정 기준 이상이면 스케일 아웃하는 용도로 사용 가능

2. RequestCountPerTarget
각 인스턴스가 처리하는 http 요청 수
일반적으로 인스턴스당 1,000개의 요청을 최적 값으로 설정한다고 하네요?
요청수가 많아져서 개별 인스턴스가 설정한 요청수 이상을 받게되면 확장하는 구조입니다.

3. 네트워크 트래픽 (Average Network In/Out)
말 그대로 네트워크 요청으로 인해 발생되는 in/out 데이터 양에 대한 지표입니다.

4. 메모리 사용률 (Memory Utilization)
AWS 기본 CloudWatch에서는 제공되지 않지만, CloudWatch Agent를 설정하면 모니터링 가능합니다.
**요거 시험에 응용될 수 있을 거 같아요 어떤 지표를 조건으로 ASG 정책을 설정하려고 할 때 해당 지표가 기본 CloudWatch에서 제공하는 지표냐 아니면 내가 커스텀해서 추가해야 하냐에 따라 정답이 달라질 수 있음**

## 스케일링 쿨다운 (Cooldown Period)
ASG가 스케일 인/아웃을 수행할 때, 너무 자주 변화하면 리소스 낭비가 발생할 수 있습니다.

즉 스케일 인/아웃이 수행된 후 일정 시간 동안 추가적인 스케일링을 수행하지 않습니다.

다만 지속적으로 스케일 아웃이 수행되야 할 정도로 많은 트래픽이 몰려오는 경우 이게 오히려 단점이 될 수 있으니 이것도 전략을 잘 세워야 함.
