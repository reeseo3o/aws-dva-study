## Amazon SQS (Simple Queue Service)

SQS는 애플리케이션 간 메시지를 안정적으로 저장하고 전달하는 완전 관리형 메시지 대기열 서비스입니다.

**주요 특징:**

*   **분리 (Decoupling):** 생산자(Producer)와 소비자(Consumer)를 분리하여 시스템의 탄력성과 확장성을 높입니다.
*   **메시지 처리:** 소비자는 대기열에서 메시지를 폴링(Polling)하고, 처리 후 명시적으로 삭제해야 합니다. (`ReceiveMessage`, `DeleteMessage` API 사용)
*   **표준 대기열 (Standard Queue):**
    *   높은 처리량 (사실상 무제한)
    *   최소 한 번 전송 보장 (At-Least-Once Delivery) - 메시지가 중복될 수 있음
    *   최선 노력 순서 지정 (Best-Effort Ordering) - 순서가 보장되지 않음
*   **FIFO 대기열 (First-In, First-Out Queue):**
    *   메시지 순서 보장 (선입선출)
    *   정확히 한 번 처리 보장 (Exactly-Once Processing) - 5분 간격 내 중복 제거 기능 포함 (콘텐츠 기반 또는 중복 제거 ID 사용)
    *   처리량 제한 (초당 300개 또는 배치 시 3000개)
    *   대기열 이름이 `.fifo`로 끝나야 함
    *   메시지 그룹 ID를 통해 그룹 내 순서 보장 및 병렬 처리 가능
*   **가시성 제한 시간 (Visibility Timeout):** 소비자가 메시지를 폴링하여 처리하는 동안 다른 소비자가 해당 메시지를 보지 못하도록 숨기는 시간 (기본 30초, 최대 12시간). 처리 시간이 더 필요하면 `ChangeMessageVisibility` API로 연장 가능.
*   **배달 못한 편지 대기열 (Dead-Letter Queue, DLQ):** 메시지 처리 실패 횟수(최대 수신 수) 임곗값을 초과한 메시지를 격리하여 원인 분석 및 디버깅을 돕는 별도 대기열. (표준 -> 표준 DLQ, FIFO -> FIFO DLQ)
*   **지연 대기열 (Delay Queue):** 메시지를 대기열에 넣은 후 지정된 시간(최대 15분) 동안 소비자가 즉시 수신하지 못하도록 지연시킴 (`DelaySeconds` 파라미터).
*   **롱 폴링 (Long Polling):** 소비자가 폴링 시 대기열에 메시지가 없으면, 메시지가 도착하거나 제한 시간(최대 20초)이 만료될 때까지 대기. API 호출 수를 줄여 비용을 절감하고 효율성 및 응답 속도 향상 (`WaitTimeSeconds` 파라미터).
*   **확장 클라이언트 라이브러리 (Extended Client Library):** 메시지 크기 제한(256KB)을 초과하는 대용량 페이로드를 Amazon S3를 통해 간접적으로 처리.
*   **보안:** HTTPS 전송 중 암호화, KMS 키를 사용한 저장 데이터 암호화, IAM 정책 및 SQS 접근 정책(리소스 기반 정책)을 통한 세분화된 접근 제어 (교차 계정 접근, 다른 AWS 서비스 접근 허용 등).
*   **주요 사용 사례:** 마이크로서비스 간 통신 분리, 작업 대기열 관리, 비동기 워크플로우 처리, 배치 작업 처리, Auto Scaling Group과 연동하여 부하에 따른 자동 확장.

### SQS 확장 클라이언트 라이브러리 (Extended Client Library)

SQS의 메시지 크기 제한(256KB)을 초과하는 대용량 메시지를 처리하기 위한 라이브러리입니다.

**주요 특징:**

*   **메시지 크기:** 최대 2GB까지 처리 가능
*   **S3 연동:** 대용량 메시지는 자동으로 S3에 저장되고 참조됨
*   **선택적 S3 사용:** 256KB 초과 메시지만 S3에 저장하도록 설정 가능
*   **자동 관리:** S3 객체의 업로드, 다운로드, 삭제를 자동으로 처리

**작동 방식:**

1. 생산자(Producer)가 대용량 메시지 전송
2. 확장 클라이언트가 메시지를 S3에 자동 업로드
3. S3 객체 참조를 포함한 작은 메시지를 SQS에 전송
4. 소비자(Consumer)가 메시지 수신 시 확장 클라이언트가 S3에서 원본 메시지 자동 다운로드
5. 메시지 처리 완료 후 SQS 메시지와 S3 객체 자동 삭제

**구현 요구사항:**

*   Java용 AWS SDK와 확장 클라이언트 라이브러리 필요
*   S3 버킷과 SQS 큐는 동일 리전에 위치
*   적절한 IAM 권한 설정 (S3, SQS 모두에 대해)
*   SQS 요금과 S3 스토리지/요청 요금 모두 발생

**주요 사용 사례:**

*   대용량 파일 처리 워크플로우 (이미지/비디오 처리)
*   마이크로서비스 간 대용량 데이터 전송
*   대규모 데이터 분석 및 처리 작업
*   데이터 마이그레이션 작업

**모범 사례:**

*   256KB 이하 메시지는 일반 SQS 사용 권장
*   대용량 메시지만 선별적으로 S3 처리하도록 설정
*   S3 객체의 수명 주기 정책 설정 고려
*   적절한 모니터링 및 오류 처리 구현

## Amazon SNS (Simple Notification Service)

SNS는 게시/구독(Pub/Sub) 모델 기반의 완전 관리형 메시징 서비스로, 하나의 메시지를 다수의 구독자에게 효율적으로 푸시(전달)합니다.

**주요 특징:**

*   **게시/구독 (Publish/Subscribe):** 생산자는 메시지를 '주제(Topic)'에 한 번 게시하고, 해당 주제를 구독하는 모든 엔드포인트(구독자)에게 메시지가 동시에 전달됩니다.
*   **다양한 구독자 유형 지원:** SQS, Lambda, HTTP/S 엔드포인트, 이메일, SMS, 모바일 푸시 알림 (GCM, APNS, ADM), Kinesis Data Firehose 등 다양한 대상으로 메시지를 전송할 수 있습니다.
*   **Fan Out 패턴:** 하나의 SNS 주제에 여러 SQS 대기열이나 Lambda 함수 등을 구독시켜, 단일 이벤트를 여러 시스템으로 동시에 분배하고 병렬 처리할 수 있게 합니다. SQS와 결합 시 데이터 지속성 및 안정적인 처리 보장.
*   **메시지 필터링:** 구독자는 구독 시 JSON 기반의 필터 정책을 설정하여, 특정 속성이나 값을 가진 메시지만 선별적으로 수신할 수 있습니다.
*   **SNS FIFO 주제:** SQS FIFO와 유사하게 메시지 순서 보장 및 정확히 한 번 전송 기능을 제공합니다. 오직 SQS FIFO 대기열만 구독자로 사용할 수 있습니다.
*   **높은 확장성 및 처리량:** 주제당 수백만 명 이상의 구독자를 지원하며, 별도의 처리량 프로비저닝이 필요 없습니다.
*   **데이터 지속성 없음:** SNS는 메시지를 저장하지 않습니다. 메시지는 구독자에게 전달된 후 즉시 삭제됩니다. (지속성이 필요하면 SQS 등과 연계)
*   **보안:** SQS와 유사하게 HTTPS 전송 중 암호화, KMS 저장 데이터 암호화, IAM 정책 및 SNS 접근 정책(리소스 기반 정책)을 통해 접근 제어.
*   **주요 사용 사례:** 시스템 이벤트 알림, 사용자 알림(이메일, SMS, 푸시), 마이크로서비스 간 이벤트 기반 통신(Fan Out), S3 이벤트 등 AWS 서비스 이벤트 연동, 실시간 데이터 배포.

## Amazon Kinesis

Kinesis는 실시간 스트리밍 데이터를 수집, 처리, 분석하기 위한 AWS 서비스 제품군입니다.

### Kinesis Data Streams

*   **실시간 데이터 스트리밍:** 대규모 실시간 데이터(클릭스트림, 로그, IoT 센서 데이터 등)를 지속적으로 수집하고 여러 소비자가 동시에 접근하여 처리할 수 있는 서비스입니다.
*   **데이터 보존 및 재생 (Replay):** 데이터를 스트림 내에 설정된 기간(기본 24시간, 최대 365일) 동안 안정적으로 보존하며, 소비자는 필요에 따라 과거 데이터를 다시 읽어 처리(재생)할 수 있습니다.
*   **샤드 (Shards):** 스트림 처리 용량의 기본 단위입니다. 각 샤드는 특정 쓰기(초당 1MB 또는 1000개 레코드) 및 읽기(초당 2MB) 용량을 가집니다.
*   **용량 모드:**
    *   **프로비저닝 모드:** 필요한 샤드 수를 사용자가 직접 예측하고 수동으로 관리합니다. 시간당 샤드 수에 따라 비용이 부과됩니다.
    *   **온디맨드 모드:** 실제 트래픽 양에 따라 AWS가 자동으로 샤드 수를 조정합니다. 인프라 관리가 필요 없으며, 스트림 시간당 요금 및 데이터 처리량에 따라 비용이 부과됩니다.
*   **순서 보장:** 동일한 파티션 키(Partition Key)를 가진 레코드들은 해당 샤드 내에서 순서대로 처리됩니다.
*   **소비자:** KCL(Kinesis Client Library), Lambda, Kinesis Data Firehose, Amazon Managed Service for Apache Flink 등 다양한 방식으로 데이터를 소비할 수 있습니다. 향상된 팬아웃(Enhanced Fan-Out)을 통해 소비자당 샤드 읽기 처리량을 높일 수 있습니다.
*   **보안:** HTTPS 전송 중 암호화, KMS 저장 데이터 암호화.
*   **주요 사용 사례:** 실시간 분석 대시보드, 실시간 이상 감지, 로그 및 이벤트 데이터의 실시간 수집 및 처리, 클릭스트림 분석, IoT 데이터 처리.

### Kinesis Data Firehose

*   **데이터 로딩 및 전송:** 스트리밍 데이터를 거의 실시간(Near Real-Time)으로 수집하여 S3, Redshift, OpenSearch Service, Splunk 등 다양한 목적지로 안정적으로 전송(로드)하는 완전 관리형 서비스입니다.
*   **서버리스 및 자동 확장:** 별도의 인프라 관리나 용량 계획 없이 자동으로 확장됩니다.
*   **데이터 변환 (선택 사항):** AWS Lambda 함수를 통합하여 데이터를 목적지로 전송하기 전에 형식 변환, 필터링, 보강 등의 사용자 정의 변환 작업을 수행할 수 있습니다.
*   **내장 형식 변환 및 압축:** 데이터를 Parquet 또는 ORC와 같은 컬럼 기반 형식으로 변환하거나 GZIP, Snappy 등으로 압축하여 저장 효율성을 높일 수 있습니다.
*   **버퍼링:** 데이터를 즉시 전송하지 않고 일정 크기(MB) 또는 시간(초) 동안 버퍼링한 후 일괄적으로 목적지에 전송하여 효율성을 높입니다. (거의 실시간 특성의 이유)
*   **데이터 지속성/재생 불가:** Firehose 자체는 데이터를 저장하지 않으므로 재생 기능이 없습니다. 전송 실패 데이터나 모든 데이터를 백업 목적으로 S3에 저장하는 옵션은 제공합니다.
*   **소스:** Kinesis Data Streams, Direct PUT (SDK, Kinesis Agent), CloudWatch Logs/Events, AWS IoT 등.
*   **주요 사용 사례:** 스트리밍 ETL(추출, 변환, 로드), 로그 및 이벤트 데이터의 데이터 레이크/웨어하우스 적재, IoT 데이터 아카이빙 및 분석 준비.

### Amazon Managed Service for Apache Flink

*   **실시간 스트림 처리 및 분석:** Apache Flink 프레임워크를 사용하여 Kinesis Data Streams 또는 Amazon MSK(Managed Streaming for Apache Kafka)의 데이터를 실시간으로 복잡하게 처리하고 분석하는 완전 관리형 서비스입니다. (이전 명칭: Kinesis Data Analytics for Apache Flink)
*   **관리형 Flink 환경:** Flink 애플리케이션 실행에 필요한 인프라 프로비저닝, 관리, 자동 확장, 내결함성(체크포인트/스냅샷) 등을 AWS가 처리합니다.
*   **다양한 언어 지원:** SQL, Java, Scala 등 Flink에서 지원하는 언어로 애플리케이션 개발 가능.
*   **주요 사용 사례:** 복잡한 상태 기반의 실시간 분석, 스트리밍 데이터에 대한 정교한 변환 및 집계, 실시간 이상 탐지 시스템 구축.

## SQS vs SNS vs Kinesis Data Streams 비교 요약

| 기능          | SQS (Simple Queue Service)                 | SNS (Simple Notification Service)            | Kinesis Data Streams                       |
| :------------ | :----------------------------------------- | :----------------------------------------- | :----------------------------------------- |
| 모델          | 대기열 (Queue), **Pull** 모델                | 주제 (Topic), **Push** (Pub/Sub) 모델        | 스트림 (Stream), Pull 또는 Push (Enhanced Fan-Out) |
| 소비자 관계   | 1 메시지 : 1 소비자 (처리 후 명시적 삭제)   | 1 메시지 : 다수 구독자 (메시지 복사본 전달) | 다수 소비자가 동일 데이터 독립적 읽기 가능 |
| 데이터 지속성 | 메시지 보존 기간 설정 (기본 4일, 최대 14일) | 없음 (메시지 전달 후 즉시 삭제)          | 있음 (기본 24시간, 최대 365일), **데이터 재생 가능** |
| 순서 보장     | **FIFO 대기열** 옵션 제공                    | **FIFO 주제** 옵션 제공 (SQS FIFO 구독자 필요) | **파티션 키** 기준 순서 보장               |
| 처리량        | 높음 (Standard), 제한됨 (FIFO)               | 높음 (프로비저닝 불필요)                    | **샤드** 기반 (용량 모드에 따라 관리/자동 조정) |
| 주요 특징     | 애플리케이션 분리, 작업 관리, 내결함성        | 이벤트 알림, Fan Out 패턴, 다양한 엔드포인트 | 실시간 데이터 처리, 데이터 영속성, 재생   |
| 주요 용도     | 비동기 작업 처리, 마이크로서비스 디커플링     | 실시간 알림, 이벤트 기반 아키텍처           | 실시간 분석, 로그 수집, IoT 데이터 스트리밍 |
