## AWS Elastic Beanstalk


### 1. AWS Elastic Beanstalk 소개 및 필요성

**기존 애플리케이션 배포 아키텍처의 복잡성**

일반적인 웹 애플리케이션은 로드 밸런서, 오토 스케일링 그룹(ASG) 내 다중 가용 영역(AZ)에 걸친 EC2 인스턴스, 그리고 백엔드의 RDS 데이터베이스(경우에 따라 읽기 전용 복제본 포함) 및 ElastiCache 등으로 구성됩니다. 이러한 인프라를 애플리케이션마다 반복적으로 구축하고 관리하는 것은 개발자에게 상당한 부담입니다. 용량 프로비저닝, 로드 밸런싱, 오토 스케일링 설정, 데이터베이스 관리, 모니터링 등 신경 써야 할 부분이 많습니다.

**Elastic Beanstalk: 개발자 중심의 배포 솔루션**

Elastic Beanstalk는 이러한 복잡성을 해결하기 위해 등장했습니다. 개발자가 인프라 관리의 부담에서 벗어나 **코드 작성에만 집중**할 수 있도록 지원하는 **관리형 서비스**입니다. EC2, ASG, ELB, RDS 등 AWS의 핵심 구성 요소들을 활용하여 애플리케이션 배포 및 운영에 필요한 환경을 **자동으로 프로비저닝하고 관리**해줍니다.

**주요 이점**

*   **인프라 관리 부담 감소:** 용량 프로비저닝, 로드 밸런싱, 오토 스케일링, 상태 모니터링 등을 자동화합니다.
*   **개발 생산성 향상:** 개발자는 코드 배포에만 집중할 수 있습니다.
*   **다양한 언어 및 환경 지원:** Java, .NET, PHP, Node.js, Python, Ruby, Go, Docker 등 폭넓은 기술 스택을 지원합니다.
*   **통합된 관리 인터페이스:** 여러 AWS 서비스를 하나의 콘솔에서 관리할 수 있습니다.
*   **비용 효율성:** Beanstalk 서비스 자체는 무료이며, 사용된 기본 AWS 리소스(EC2, RDS 등)에 대해서만 비용을 지불합니다.
*   **유연한 배포 및 업데이트:** 다양한 배포 전략을 제공하여 다운타임을 최소화하고 안정적인 업데이트를 지원합니다.

### 2. Elastic Beanstalk 핵심 구성 요소

Elastic Beanstalk 환경을 이해하기 위한 주요 개념

*   **애플리케이션 (Application):** 배포하려는 코드의 논리적인 그룹입니다. 환경, 버전, 구성 등을 포함하는 최상위 컨테이너 역할을 합니다.
*   **애플리케이션 버전 (Application Version):** 특정 시점의 애플리케이션 코드 번들(예: ZIP 파일)입니다. 버전 관리를 통해 이전 버전으로 쉽게 롤백할 수 있습니다. (v1, v2, v3...)
*   **환경 (Environment):** 특정 애플리케이션 버전을 실행하는 AWS 리소스의 모음입니다.
    *   하나의 환경은 한 번에 하나의 애플리케이션 버전만 실행할 수 있습니다.
    *   개발(Dev), 테스트(Test), 운영(Production) 등 목적에 따라 여러 환경을 생성하여 관리할 수 있습니다.
*   **환경 티어 (Environment Tier):** 환경의 목적에 따라 두 가지 유형으로 나뉩니다. (아래 섹션에서 상세 설명)
    *   **웹 서버 티어 (Web Server Tier):** HTTP 요청을 처리하는 웹 애플리케이션용 환경입니다.
    *   **작업자 티어 (Worker Tier):** 시간이 오래 걸리는 작업, 예약된 작업, 비동기 처리 등 백그라운드 프로세싱에 적합합니다.

**작동 프로세스**

1.  **애플리케이션 생성:** Beanstalk에서 관리할 애플리케이션 단위를 정의합니다.
2.  **애플리케이션 버전 업로드:** 배포할 코드(예: ZIP 파일)를 업로드합니다.
3.  **환경 시작:** 업로드된 버전을 실행할 환경(웹 서버 또는 작업자 티어)을 구성하고 시작합니다.
4.  **환경 관리:** 배포된 애플리케이션을 모니터링하고, 필요에 따라 새 버전을 배포하거나 환경 설정을 변경합니다.

### 3. Elastic Beanstalk 환경 티어: 웹 서버 vs. 작업자

Elastic Beanstalk는 애플리케이션의 역할에 따라 두 가지 환경 티어를 제공합니다.

*   **웹 서버 환경 (Web Server Environment)**
    *   **목적:** 사용자의 HTTP 요청을 직접 처리하는 표준 웹 애플리케이션에 적합합니다.
    *   **아키텍처:** 로드 밸런서(ELB)가 들어오는 트래픽을 여러 가용 영역에 분산된 오토 스케일링 그룹(ASG) 내의 EC2 인스턴스로 전달하는 익숙한 구조입니다.
    *   **확장:** 트래픽 부하, CPU 사용률 등 정의된 메트릭에 따라 ASG가 EC2 인스턴스 수를 자동으로 조절합니다.

*   **작업자 환경 (Worker Environment)**
    *   **목적:** 시간이 오래 걸리는 작업, 예약된 작업, 비동기 처리 등 백그라운드 프로세싱에 적합합니다.
    *   **아키텍처:** 클라이언트가 직접 인스턴스에 접근하지 않습니다. 대신, 작업 요청(메시지)이 Amazon SQS(Simple Queue Service) 대기열에 추가됩니다. ASG 내의 EC2 인스턴스(작업자)들은 이 SQS 대기열에서 메시지를 가져와(Polling) 처리할 것이기 때문입니다.
    *   **확장:** SQS 대기열에 쌓인 메시지 수에 따라 ASG가 작업자 인스턴스 수를 자동으로 조절합니다. 메시지가 많아지면 인스턴스 수가 늘어나고, 줄어들면 인스턴스 수도 줄어듭니다.
    *   **활용:** 웹 서버 환경과 함께 사용하여, 웹 서버가 시간이 오래 걸리는 작업을 직접 처리하는 대신 SQS 대기열에 메시지를 보내고 작업자 환경이 이를 비동기적으로 처리하도록 구성할 수 있다는 것입니다. (예: 이미지 리사이징, 비디오 인코딩, 대량 이메일 발송)

### 4. Elastic Beanstalk 배포 모드: 단일 인스턴스 vs. 고가용성

환경을 생성할 때 선택할 수 있는 두 가지 기본 배포 모드가 있습니다.

*   **단일 인스턴스 (Single Instance)**
    *   **구성:** 단일 EC2 인스턴스와 Elastic IP 주소로 구성됩니다. 필요에 따라 RDS 데이터베이스를 추가할 수 있습니다.
    *   **용도:** 개발 및 테스트 목적에 적합합니다. 빠르고 간단하게 환경을 구성할 수 있습니다.
    *   **단점:** 가용성이 낮습니다. 해당 인스턴스에 장애가 발생하면 서비스 전체가 중단됩니다. 로드 밸런싱 및 자동 확장을 지원하지 않습니다.
*   **고가용성 (High Availability - Load Balanced)**
    *   **구성:** 로드 밸런서(ELB)가 여러 가용 영역(AZ)에 걸쳐 있는 오토 스케일링 그룹(ASG) 내의 다중 EC2 인스턴스로 트래픽을 분산합니다. 필요에 따라 다중 AZ RDS 데이터베이스(Master/Standby)를 구성할 수 있습니다.
    *   **용도:** 실제 운영(Production) 환경에 적합합니다. 높은 가용성과 확장성을 제공합니다.
    *   **장점:** 단일 인스턴스 또는 가용 영역 장애 시에도 서비스 연속성을 보장합니다. 트래픽 변화에 따라 자동으로 인스턴스 수를 조절하여 비용 효율성과 성능을 최적화합니다.

### 5. Elastic Beanstalk 배포 전략 심층 분석

Elastic Beanstalk는 애플리케이션 새 버전을 기존 환경에 배포할 때 다운타임, 배포 속도, 비용, 롤백 용이성 등을 고려하여 다양한 전략을 선택할 수 있도록 지원합니다.

#### 5.1. All at Once (한 번에 모두)

*   **작동 방식:**
    1.  실행 중인 모든 EC2 인스턴스에서 현재 버전의 애플리케이션을 중지합니다. (모든 인스턴스가 잠시 트래픽 처리 불가 상태가 됨)
    2.  모든 인스턴스에 동시에 새 버전의 애플리케이션을 배포하고 시작합니다.
*   **특징:**
    *   **배포 시간:** 가장 빠름
    *   **다운타임:** 발생 (애플리케이션이 중지되는 시간 동안)
    *   **비용:** 추가 비용 없음 (기존 인스턴스 활용)
    *   **용량:** 배포 중 잠시 용량 없음
    *   **롤백:** 실패 시 수동으로 이전 버전을 다시 'All at Once' 방식으로 배포해야 함
*   **적합한 환경:** 개발, 빠른 반복, 다운타임 허용

#### 5.2. Rolling (롤링)

*   **작동 방식:**
    1.  전체 인스턴스를 **버킷(Bucket)** 또는 **배치(Batch)**라는 작은 그룹 단위로 나눕니다. (버킷 크기는 개수 또는 백분율로 설정 가능)
    2.  첫 번째 버킷의 인스턴스에서 애플리케이션을 중지하고 새 버전을 배포합니다.
    3.  첫 번째 버킷의 배포가 성공하고 인스턴스들이 정상 상태가 되면, 다음 버킷으로 이동하여 동일한 과정을 반복합니다. 모든 버킷이 업데이트될 때까지 순차적으로 진행합니다.
*   **특징:**
    *   **배포 시간:** 'All at Once'보다 느림 (버킷 단위 순차 진행)
    *   **다운타임:** 없음 (항상 일부 인스턴스는 이전 또는 새 버전으로 실행 중)
    *   **비용:** 추가 비용 없음 (기존 인스턴스 활용)
    *   **용량:** 배포 중에도 **항상 전체 용량 유지** (추가 배치 덕분)
    *   **롤백:** 배포 실패 시, 실패한 버킷까지의 변경 사항을 롤백하는 데 시간이 걸릴 수 있음. 진행 중이던 롤링 업데이트를 취소하고 수동 롤백 필요.
*   **적합한 환경:** 다운타임이 허용되지 않고, 배포 중에도 **항상 전체 서비스 용량을 유지**해야 하는 운영 환경.

#### 5.3. Rolling with Additional Batch (추가 배치를 사용한 롤링)

*   **작동 방식:**
    1.  'Rolling'과 유사하게 버킷 단위로 배포를 진행하지만, 시작하기 전에 **새로운 EC2 인스턴스로 구성된 추가 배치(버킷)**를 먼저 생성하고 여기에 새 버전을 배포합니다.
    2.  이후 기존 인스턴스들을 버킷 단위로 순차적으로 업데이트합니다. (기존 인스턴스 중지 -> 새 버전 배포)
    3.  모든 기존 인스턴스 업데이트가 완료되면, 처음에 추가했던 임시 인스턴스 배치를 종료합니다.
*   **특징:**
    *   **배포 시간:** 'Rolling'과 비슷하거나 약간 더 오래 걸릴 수 있음 (초기 추가 배치 생성 시간)
    *   **다운타임:** 없음
    *   **비용:** **약간의 추가 비용 발생** (배포 시간 동안 임시 인스턴스 운영)
    *   **용량:** 배포 중에도 **항상 전체 용량 유지** (추가 배치 덕분)
    *   **롤백:** 'Rolling'과 유사하게 수동 롤백 필요.
*   **적합한 환경:** 다운타임이 허용되지 않고, 배포 중에도 **항상 전체 서비스 용량을 유지**해야 하는 운영 환경.

#### 5.4. Immutable (변경 불가능)

*   **작동 방식:**
    1.  기존 인스턴스(ASG)는 그대로 둔 채, **완전히 새로운 임시 오토 스케일링 그룹(ASG)**을 생성합니다.
    2.  이 임시 ASG에 새 버전의 애플리케이션이 설치된 **새로운 EC2 인스턴스들**을 배포합니다. (보통 상태 확인을 위해 먼저 1개를 띄우고, 정상이면 나머지 인스턴스 생성)
    3.  새로운 인스턴스들이 모두 준비되고 상태 검사를 통과하면, 로드 밸런서가 트래픽을 기존 ASG에서 새로운 임시 ASG로 **한 번에 전환**합니다. (기존 ASG 인스턴스들은 트래픽을 받지 않게 됨)
    4.  트래픽 전환이 완료되면, 기존 ASG와 인스턴스들을 종료(제거)합니다. 임시 ASG가 새로운 메인 ASG가 됩니다.
*   **특징:**
    *   **배포 시간:** 가장 오래 걸림 (새로운 ASG와 인스턴스 전체를 생성해야 함)
    *   **다운타임:** 없음
    *   **비용:** **가장 많은 추가 비용 발생** (배포 시간 동안 거의 두 배의 인스턴스 운영)
    *   **용량:** 배포 중에도 **항상 전체 용량 유지** (추가 배치 덕분)
    *   **롤백:** **매우 빠르고 안전함.** 실패 감지 시 즉각적인 롤백 가능.
*   **적합한 환경:** 다운타임이 절대 허용되지 않고, 배포 실패 시 **빠른 롤백 필수**, 비용 < 안정성

#### 5.5. Blue/Green (블루/그린) - Beanstalk 직접 기능 아님

*   **개념:** Beanstalk의 내장 배포 전략은 아니지만, 환경 관리 기능을 활용하여 구현할 수 있는 고급 배포 패턴입니다.
*   **작동 방식:**
    1.  현재 운영 환경(예: **Blue**)과 **동일한 구성**으로 **별도의 새로운 Elastic Beanstalk 환경**을 생성합니다.
    2.  새로운 Green 환경에 애플리케이션의 새 버전을 배포하고 충분히 테스트합니다.
    3.  테스트가 완료되면, **Route 53**과 같은 DNS 설정을 변경하여 트래픽을 기존 환경에서 새로 만든 환경으로 점진적 또는 한 번에 이동시킵니다.
    4.  Green 환경이 안정적으로 운영되는 것을 확인한 후, 이전 Blue 환경을 종료하고 URL을 전환해 그린 환경을 메인 환경으로 만듭니다.
*   **특징:**
    *   **배포 시간:** 새로운 환경 전체를 구성하고 테스트해야 하므로 매우 오래 걸림.
    *   **다운타임:** 없음 (DNS 전파 시간에 따라 약간의 지연이 발생할 수 있음)
    *   **비용:** **가장 많은 비용 발생** (두 개의 완전한 환경을 동시에 운영)
    *   **용량:** 두 배의 용량 필요
    *   **롤백:** **매우 빠르고 자동화됨.** 실패 감지 시 즉각적인 롤백 가능.
    *   **기타:** 배포 전 **별도의 환경에서 충분한 테스트**가 가능합니다. Beanstalk 내장 기능이 아니므로 **수동 설정 및 관리**(특히 DNS)가 필요합니다.
*   **적합한 환경:** 매우 중요한 운영 환경에서 위험을 최소화하고 싶은 때, 새 버전 배포 전 별도의 동일 환경에서 철저한 검증이 필요할 때 사용합니다.

#### 5.6. Traffic Splitting (트래픽 분할 - Canary)

*   **개념:** 새 버전의 안정성을 검증하기 위해 **실제 운영 트래픽의 일부**(작은 비율)만 새 버전으로 보내 테스트하는 방식입니다. 카나리(Canary) 배포와 유사합니다.
*   **작동 방식:**
    1.  기존 메인 ASG와 **동일한 용량**의 **임시 오토 스케일링 그룹(ASG)**을 생성하고 여기에 새 버전을 배포합니다.
    2.  로드 밸런서 설정을 통해 **지정된 비율**(예: 10%)의 트래픽만 임시 ASG(새 버전)로 보내고, 나머지 트래픽(예: 90%)은 기존 메인 ASG(이전 버전)로 보냅니다.
    3.  **지정된 시간 동안** 새 버전의 성능과 안정성(메트릭, 로그 등)을 모니터링합니다.
    4.  **성공 시:** 문제가 없다고 판단되면, 임시 ASG의 새 인스턴스들을 메인 ASG로 이동시키고, 이전 버전 인스턴스들을 종료합니다.
    5.  **실패 시:** 문제가 감지되면 즉시 **자동 롤백**이 트리거됩니다. 임시 ASG로 보내던 트래픽을 차단하고 임시 ASG를 제거하면 되므로 매우 빠릅니다.
*   **특징:**
    *   **배포 시간:** 모니터링 시간 포함하여 다소 걸림.
    *   **다운타임:** 없음
    *   **비용:** **추가 비용 발생** (배포 및 모니터링 시간 동안 임시 ASG 운영)
    *   **용량:** 배포 중에도 **항상 전체 용량 유지** (추가 배치 덕분)
    *   **롤백:** **매우 빠르고 자동화됨.** 실패 감지 시 즉각적인 롤백 가능.
    *   **기타:** 실제 운영 트래픽을 이용하여 **새 버전의 위험을 최소화**하면서 테스트할 수 있습니다. Beanstalk에서 **자동화된 방식**으로 지원합니다.
*   **적합한 환경:** 새 버전 배포에 따른 위험을 최소화하고 싶은 운영 환경. 점진적으로 새 버전의 안정성을 검증하고 싶을 때 사용합니다.

### 7. Elastic Beanstalk 환경 구성 및 관리

#### 7.1. 구성 업데이트 및 배포 실습 요약

강의에서는 Beanstalk 콘솔을 통해 환경 구성을 변경하고 새 애플리케이션 버전을 배포하는 과정을 시연했습니다.

*   **환경 구성 변경:**
    *   `구성` > `업데이트, 모니터링 및 로깅` > `편집` 메뉴에서 배포 정책(All at once, Rolling, Immutable, Traffic Splitting 등)을 변경할 수 있습니다.
    *   배치 크기(고정값 또는 백분율) 등 세부 옵션 설정이 가능합니다.
    *   `Immutable` 배포 방식을 선택하고 적용하여 환경 업데이트를 진행했습니다.
*   **새 버전 배포:**
    *   샘플 Node.js 애플리케이션 코드를 수정 (배경색 변경) 하고 `.zip` 파일로 준비했습니다.
    *   `업로드 및 배포` 버튼을 클릭하여 새 버전 `.zip` 파일을 업로드하고 버전 레이블을 지정했습니다.
    *   배포 정책으로 `Immutable`을 선택하여 배포했습니다.
    *   이벤트 로그를 통해 `Immutable` 배포 과정(임시 ASG 생성, 새 인스턴스 시작, 상태 확인, 트래픽 전환, 이전 인스턴스 제거)을 관찰했습니다.
    *   배포 완료 후, 웹 브라우저에서 변경된 애플리케이션(파란 배경)을 확인했습니다.

#### 7.2. 환경 도메인 교체 (Swap Environment URLs)

*   **기능:** 두 개의 실행 중인 Elastic Beanstalk 환경의 CNAME 레코드를 서로 교체하여, 각 환경에 할당된 URL(도메인)을 바꾸는 기능입니다.
*   **용도:**
    *   블루/그린 배포 패턴에서 테스트가 완료된 Green 환경을 실제 운영 환경(Blue URL)으로 빠르고 안전하게 전환하는 데 주로 사용됩니다.
    *   운영 환경 복제본에 새 버전을 배포 및 테스트한 후, 원래 운영 환경 URL과 교체하여 업데이트를 완료합니다.
*   **작동 방식:** DNS 레코드 변경을 통해 이루어지므로, 실제 애플리케이션 코드나 인프라 변경 없이 URL만 교체됩니다. DNS 전파 시간에 따라 약간의 지연이 발생할 수 있습니다.
*   **실습 요약:**
    *   `prod`(파란색) 환경과 `dev`(녹색) 환경의 도메인을 교체하여, 트래픽을 기존 환경에서 새로 만든 환경으로 이동시킵니다.
    *   `dev`를 선택하고 Swap을 클릭합니다.
    *   DNS 업데이트는 DNS와 관련이 있습니다.
    *   업데이트 시간이 조금 걸립니다.
    *   DNS 업데이트가 완료되면 환경이 교환됩니다.

### 8. Elastic Beanstalk 마이그레이션 전략

실제 운영 환경에서는 초기 구성 이후 로드 밸런서 종류를 바꾸거나, Beanstalk 내에 생성했던 RDS를 외부로 분리해야 하는 상황이 발생할 수 있습니다. Beanstalk는 한 번 생성된 환경의 특정 요소(특히 로드 밸런서 유형, RDS 통합 여부)를 직접 변경하는 것을 지원하지 않으므로, 마이그레이션 작업이 필요합니다.

#### 8.1. 로드 밸런서 유형 변경 마이그레이션 (예: Classic -> Application LB)

*   **문제:** Beanstalk 환경 생성 시 선택한 로드 밸런서 유형(Classic, Application, Network)은 **생성 후 변경이 불가능**합니다.
*   **해결 절차:**
    1.  **새 환경 수동 생성:** 기존 환경과 **동일한 구성**을 가지지만, **원하는 새 로드 밸런서 유형**을 선택하여 **새로운 Elastic Beanstalk 환경**을 생성합니다.
    2.  **애플리케이션 배포:** 새로 생성한 환경에 현재 운영 중인 애플리케이션 버전을 배포합니다.
    3.  **트래픽 전환 (DNS 업데이트):** 모든 테스트가 완료되면, **CNAME 교체**(Beanstalk의 '환경 URL 교체' 기능) 또는 **Route 53** 등 DNS 설정을 변경하여 트래픽을 기존 환경에서 새로 만든 환경으로 이동시킵니다.
    4.  **기존 환경 삭제:** 새 환경이 안정화되면 기존 환경을 삭제합니다.

#### 8.2. RDS 데이터베이스 분리 마이그레이션 (Beanstalk 관리 -> 외부 관리)

*   **문제:** 개발/테스트 단계에서는 편의상 Beanstalk 환경 내에 RDS 데이터베이스를 함께 생성하여 사용할 수 있습니다. 하지만 이 경우, **데이터베이스의 수명 주기가 Beanstalk 환경의 수명 주기에 종속**됩니다.
*   **해결 절차:**
    1.  **RDS 스냅샷 생성:** 만약을 대비하여 현재 Beanstalk 환경 내 RDS 데이터베이스의 **스냅샷**을 생성하여 데이터를 백업합니다.
    2.  **RDS 삭제 방지 설정:** AWS RDS 콘솔로 이동하여 해당 데이터베이스 인스턴스의 **삭제 방지(Deletion Protection)** 옵션을 활성화합니다.
    3.  **새 환경 생성 (RDS 제외):** 기존 환경과 동일한 구성으로 **새로운 Elastic Beanstalk 환경**을 생성하되, 이번에는 **RDS 데이터베이스를 포함하지 않도록** 설정합니다.
    4.  **애플리케이션 배포 및 테스트:** 새로 생성한 환경에 애플리케이션을 배포하고, 기존 데이터베이스에 정상적으로 연결하는지 충분히 테스트합니다.
    5.  **트래픽 전환 (DNS 업데이트):** CNAME 교체 또는 Route 53을 사용하여 트래픽을 기존 환경에서 새로 만든 환경으로 이동시킵니다.
    6.  **기존 환경 삭제:** 새 환경이 안정화되면 기존 환경을 삭제합니다.

### 9. 리소스 정리

실습 및 데모 환경 운영 후에는 불필요한 비용 발생을 막기 위해 생성된 리소스를 정리해야 합니다.

*   **방법:** Elastic Beanstalk 콘솔에서 해당 **애플리케이션** 자체를 삭제하면, 그 애플리케이션에 속한 모든 환경(및 관련 CloudFormation 스택)과 리소스(EC2, ASG, ELB, Security Group 등)가 **한 번에 삭제**됩니다.

### 10. 애플리케이션 버전 수명 주기 정책

Elastic Beanstalk에서는 애플리케이션 버전의 효율적인 관리를 위해 수명 주기 정책을 제공합니다. 이를 통해 오래된 버전을 자동으로 정리하고 스토리지 비용을 최적화할 수 있습니다.

#### 10.1. 수명 주기 정책의 목적

*   **버전 관리:** 애플리케이션 버전 할당량 초과 방지
*   **비용 최적화:** S3 스토리지 비용 절감
*   **자동화:** 오래된 버전의 자동 정리

#### 10.2. 주요 설정 옵션

1.  **버전 제한 방식**
    *   **총 개수 기준 (Set application versions limit by count)**
        *   최소값: 1개
        *   권장값: 15-25개
        *   새로운 버전은 카운트에 포함되지 않음
        *   설정된 개수를 초과하면 가장 오래된 버전부터 삭제
    *   **기간 기준 (Set application versions limit by age)**
        *   최소값: 1일
        *   권장값: 30-90일
        *   설정된 기간이 지난 버전 자동 삭제
        *   현재 환경에서 사용 중인 버전은 보호됨

2.  **소스 번들 보존 설정**
    *   **보존 (Retain source bundle in S3)**
        *   S3에 소스 코드 유지
        *   버전 복원이나 참조가 필요할 때 유용
        *   추가 S3 스토리지 비용 발생
    *   **삭제 (Delete source bundle from S3)**
        *   버전 삭제 시 S3에서 소스 코드도 함께 삭제
        *   스토리지 비용 절감
        *   삭제된 소스 코드는 복구 불가

#### 10.3. 작동 방식

1.  새로운 애플리케이션 버전이 업로드되면 수명 주기 정책 확인
2.  설정된 제한 조건(개수 또는 기간) 체크
3.  조건 초과 시 이전 버전 삭제 (한 번에 최대 100개)
4.  소스 번들 보존 설정에 따라 S3의 소스 코드 처리

#### 10.4. 환경별 권장 설정

1.  **개발/테스트 환경**
    *   짧은 보존 기간: 7-14일
    *   적은 버전 수: 5-10개
    *   소스 번들 삭제 고려 가능

2.  **프로덕션 환경**
    *   긴 보존 기간: 60-90일
    *   충분한 버전 수: 20-25개
    *   소스 번들 보존 권장
    *   중요 버전은 수동 보호 설정

#### 10.5. 주의사항

*   현재 실행 중인 환경에서 사용되는 버전은 자동 삭제되지 않음
*   한 번의 정책 적용으로 최대 100개 버전까지만 삭제
*   수동으로 버전을 삭제할 경우 소스 번들도 함께 삭제됨
*   삭제된 소스 번들은 복구 불가능
*   버전 제한은 새로운 버전 생성 시에만 적용됨

#### 10.6. 모범 사례

*   **정기적인 정책 검토**
    *   버전 사용 패턴 분석
    *   스토리지 비용 모니터링
    *   필요에 따라 제한값 조정

*   **중요 버전 보호**
    *   프로덕션 릴리스 버전 표시
    *   롤백 지점 보존
    *   주요 마일스톤 버전 보호

*   **문서화**
    *   버전 명명 규칙 수립

이러한 수명 주기 정책을 통해 애플리케이션 버전을 효율적으로 관리하고, 불필요한 비용을 절감하면서도 중요한 버전은 안전하게 보존할 수 있습니다.

## Beanstalk Extensions (확장)

### .ebextensions 개요
- 배포 zip 파일에 `.ebextensions/` 폴더를 포함하여 환경을 사용자 지정할 수 있습니다
- YAML 또는 JSON 형식의 `.config` 파일을 사용하여 구성
- 콘솔에서 설정하던 모든 것들을 코드로 관리 가능
- 리소스 추가 가능 (예: ElastiCache, RDS 등)
- 추가된 리소스는 Beanstalk 환경 삭제 시 함께 삭제됨

### .ebextensions 위치 및 구조
- `.ebextensions` 폴더는 반드시 애플리케이션 소스 번들의 최상위 디렉토리에 위치해야 함
- 폴더 내의 모든 구성 파일은 `.config` 확장자를 가져야 함 (예: `logging.config`, `security.config`)
- 구성 파일은 YAML 또는 JSON 형식으로 작성

### 주요 기능
1. **환경 사용자 지정**
   - 패키지 설치
   - Linux/Windows 운영 체제 설정
   - 애플리케이션 구성 파일 생성/수정
   - 서비스 실행/중지
   - 사용자/그룹 생성
   - 셸 명령 실행

2. **AWS 리소스 관리**
   - CloudFormation 리소스 형태로 동작
   - 추가 AWS 리소스 생성 및 구성
   - 리소스 간 종속성 관리
   - 환경 변수 설정

3. **고급 구성**
   - 콘솔 UI로 설정 불가능한 항목도 코드로 구성 가능
   - 배포 전략 설정
   - 오토 스케일링 규칙 정의
   - 로드 밸런서 구성

### 작동 원리
- Beanstalk는 내부적으로 CloudFormation 기반으로 동작
- `.ebextensions` 내의 리소스는 CloudFormation 리소스로 변환되어 처리
- 환경 생성/업데이트 시 구성 파일이 순차적으로 처리됨
- 구성 파일의 이름 알파벳 순서대로 처리

### 모범 사례
1. **명명 규칙**
   - 구성 파일은 목적을 명확히 나타내는 이름 사용
   - 알파벳 순서를 고려하여 실행 순서 제어

2. **버전 관리**
   - `.ebextensions`를 소스 코드와 함께 버전 관리
   - 변경 사항을 문서화하고 추적

3. **테스트**
   - 새로운 구성을 프로덕션에 적용하기 전에 테스트 환경에서 검증
   - 롤백 계획 수립

4. **보안**
   - 민감한 정보는 환경 변수나 파라미터 스토어 사용
   - 적절한 IAM 권한 설정

## Beanstalk 환경 복제 (Cloning)
기존 환경을 동일 구성으로 복제 가능

배포 버전이 있는 경우 테스트 환경 구성 시 유용

원본 환경의 설정은 유지되나, DB 데이터는 복제되지 않음

## Beanstalk 마이그레이션
### 로드 밸런서 유형 변경
환경 생성 후에는 로드밸런서 유형 변경 불가

마이그레이션 필요
- 동일한 설정으로 새 환경 생성 (로드밸런서 유형만 변경)

- CNAME 교체 또는 Route53 DNS 업데이트


### RDS 분리
RDS를 Beanstalk에서 분리해서 사용하는 것이 프로덕션에 적합

이유: Beanstalk 환경 삭제 시 RDS도 삭제될 수 있음

방법
- RDS 스냅샷 생성
- RDS 콘솔에서 삭제 방지 설정
- 새 Beanstalk 환경 구성 (RDS 제외)
- 환경 변수 등을 통해 기존 RDS 연결
- CNAME 교체 또는 블루그린 배포

## Dockerrun.aws.json

- Elastic Beanstalk의 Docker 환경에서 사용되는 구성 파일
- Docker 컨테이너의 배포 방법과 구성을 정의
- JSON 형식으로 작성되며, 애플리케이션 소스 번들의 루트에 위치

### 버전
1. **V1 (단일 컨테이너)**

   - Amazon ECS를 사용하지 않음
   - 주요 설정:
     - 이미지 위치
     - 포트 매핑
     - 볼륨
     - 로그 구성
     - 환경 변수

2. **V2 (멀티 컨테이너)**
   - 여러 Docker 컨테이너를 실행하는 환경에서 사용
   - Amazon ECS를 기반으로 동작
   - 주요 설정:
     - 컨테이너 정의
     - 컨테이너 간 링크
     - 볼륨
     - 로드 밸런싱
     - 자동 확장

### 주요 구성 요소

1. **이미지 설정**
   - Docker Hub나 private registry의 이미지 지정
   - 이미지 태그 관리
   - 인증 설정

2. **리소스 설정**
   - CPU 할당
   - 메모리 제한
   - 스토리지 구성

3. **네트워크 설정**
   - 포트 매핑
   - 컨테이너 간 통신

4. **환경 설정**

   - 로깅 구성

## DynamoDB 용량 단위 계산 예제

### 📋 문제
Node.js 애플리케이션에서 사용할 DynamoDB 테이블을 설계하고 있습니다. 이 테이블은 초당 10회의 쓰기와 초당 20회의 최종 일관성 읽기를 처리해야 하며, 두 작업 모두 모든 항목의 크기가 2KB입니다.

다음 중 테이블에 프로비저닝해야 할 가장 최적의 WCU 및 RCU는 무엇입니까?

1. 10 RCU 및 20 WCU
2. 20 RCU와 20 WCU
3. 40 RCU 및 20 WCU
4. 40 RCU 및 40 WCU

### 🧮 계산 과정

#### 1. WCU (Write Capacity Unit) 계산
```
1 WCU = 1KB/초 쓰기
2KB 항목 = 2 WCU/쓰기
초당 10회 쓰기 × 2 WCU = 20 WCU 필요
```

#### 2. RCU (Read Capacity Unit) 계산
```
1 RCU = 4KB 강력한 일관성 읽기
최종 일관성 읽기 = 강력한 일관성의 절반 RCU 소비
2KB 항목 = 1 RCU (4KB보다 작으므로)
초당 20회 읽기 ÷ 2(최종 일관성) = 10 RCU 필요
```

### ✅ 정답: 10 RCU 및 20 WCU

### 🚫 오답 분석
| 옵션 | 이유 |
|------|------|
| 20 RCU, 20 WCU | RCU가 과다 계산 (강력한 일관성 기준으로 계산) |
| 40 RCU, 20 WCU | RCU가 과다 계산 (트랜잭션 읽기 기준으로 계산) |
| 40 RCU, 40 WCU | 전체적으로 과다 계산 (트랜잭션 기준으로 계산) |

### 📌 핵심 공식

#### WCU 계산
```
필요한 WCU = 초당 쓰기 수 × (항목 크기 ÷ 1KB, 올림)
```

#### RCU 계산
```
강력한 일관성: 필요한 RCU = 초당 읽기 수 × (항목 크기 ÷ 4KB, 올림)
최종 일관성: 필요한 RCU = (초당 읽기 수 × (항목 크기 ÷ 4KB, 올림)) ÷ 2
```
