# EBS
AWS에서 제공하는 블록 스토리지 서비스로, EC2 인스턴스에 연결하여 마치 서버 내부 디스크(하드디스크나 SSD)를 쓰듯이 사용한다.

## 특징
1 .연결된 ec2 인스턴스를 중지한다고 해서 데이터가 삭제되지 않는다. (인스턴스 스토어는 삭제된다;)

2. 단순히 “파일 저장”이라기보다는 OS가 블록 단위로 I/O를 주고받는 디스크 형태로 동작한다.
이 내용은 왜 언급했냐면 익숙한 s3도 스토리지 서비스라 차이를 명확하게 하기 위해서다.
s3는 객체 단위 즉 파일 단위로 저장하고 읽는다면 EBS는 블록 단위 즉 고정된 데이터의 단위로 I/O가 처리됨.

보통 물리 디스크가 블록 단위로 필요한 데이터 부분만 입출력 하는데 그 방식을 그대로 따르도록 구성되었다고 이해하자!
그렇기에 Ec2 인스턴스는 네트워크로 연결된 ebs를 물리 디스크로 인식하고 있다.

3. Persistent Storage(09 스토리지) - 인스턴스가 종료되거나 삭제되어도 볼륨 자체를 분리해서 다른 인스턴스에 가져다 붙일 수 있음.

## EBS 스냅샷
EBS의 볼륨을 백업 이미지이다. S3에 저장된다.

EBS는 다른 가용영역의 ec2 인스턴스와 연결될 수 없다. 만약 다른 가용영역에서 생성한 ec2 인스턴스가 이 EBS 볼륨 데이터를 그대로 가져야 한다면 스냅샷을 활용하면 된다. (다른 리전에서 스냅샷을 기반으로 볼륨 복원 딸-깍)

잠깐 부가설명을 하겠다 (tmi 이해좀.. 너무 길면 스킵하자!)
EBS는 왜 다른 가용영역의 ec2 인스턴스와 연결될 수 없을까??? 결론적으론 aws가 그럴 수 없도록 설계를 해놨다.

네트워크를 깊게 이해하진 못했지만 aws를 추상적으로 이해해보자면
가용영역 단위로 네트워크를 묶어놨다. 즉 가용영역의 경계에는 엣지 역할의 라우터나 스위치 집합이 있을 것이다.

리전 수준으로 볼 땐 하위의 가용영역 모두 aws의 내부 네트워크지만 각 가용영역들은 서로가 분리된 외부 네트워크의 개념일 것이다.

즉 서로 다른 ec2 인스턴스와 ebs가 연결하기 위해서는 분리된 두 네트워크 영역간의 통신이 이루어져야 해서 지연이 좀 더 생긴다.

결국.. 네트워크 지연이 일어나는걸 막기위해 못하게 했다 라는 말을 설명하려고 길게 썼다.


# AMI
EC2 인스턴스를 시작하기 위해 필요한 OS 및 소프트웨어 구성(루트 볼륨 템플릿)을 담은 이미지.
이 AMI를 기반으로 EC2 인스턴스를 생성하면, AMI에 포함된 OS와 애플리케이션 설정이 그대로 적용된 상태로 인스턴스가 실행됨.

ec2에서 충분히 설명했다.
부가적으로 언급하자면

정말 잘 커스텀한 ami를 마켓에 파는 회사도 있다는 점.
그리고 커스텀 ami를 생성할 때는 데이터의 무결성을 위해 실행중인 인스턴스를 중지시키고 그 상태에서 스냅샷을 생성해야 한다는 점!

# Ec2 인스턴스 스토리지
EC2 인스턴스가 동작하는 물리 호스트 서버의 로컬 디스크를 사용한 임시 스토리지.
인스턴스 스토어 볼륨은 “인스턴스가 실제로 실행되는 호스트 머신의 SSD/HDD”와 직접 연결됨.
Ephemeral Storage(휘발성 저장소)라고도 불리며, 인스턴스 중지/종료 시 데이터 유실.

## 특징
EBS하고 다르게 실제 ec2가 동작하는 물리 머신과 직접적으로 연결된다.
즉 네트워크 통신인 ebs에 비해 입,출력이 훨씬 빠르게 이루어진다.

주의점은 ebs와 다르게 인스턴스를 중지하거나 삭제하면 데이터가 사라진다.
왜 그럴까?

ec2 인스턴스를 삭제하고 새로 생성할 때 기존에 연결된 인스턴스 스토어의 데이터를 그대로 사용하려면
새로 생성한 인스턴스가 기존의 물리머신에서 생성되는게 보장 되어야한다.

물론 기술적으로 불가능한건 아니지만 언제 다시 생성 또는 시작할 지 모르는 영역의 자원을 보장해줄 필요는 전혀 없을 것이다.

# EBS 볼륨 유형
gp2(General Purpose SSD)
- 범용 SSD, IOPS는 볼륨 크기에 비례(3 IOPS/GB, 최대 16,000 IOPS).
- 크기가 커질수록 자연스럽게 IOPS도 증가.
- 대부분의 범용 워크로드에 적합.
- 현재 gp3가 나온 이후 많이 대체되고 있음.

gp3(General Purpose SSD)
- gp2의 차세대 볼륨으로, 기본 IOPS와 처리량(Throughput)을 별도로 프로비저닝 가능.
- 저렴한 비용으로 더 높은 성능 조정 가능(기본 3,000 IOPS / 125MB/s).
- 추가 요금을 지불하면 IOPS와 처리량을 더 높일 수도 있음.

io1/io2(Provisioned IOPS SSD)
- 미리 설정한 IOPS를 보장하는 고성능 볼륨.
- 데이터베이스처럼 지속적이고 높은 I/O 성능이 필요한 워크로드에 적합.
- io2는 내구성이 향상된 차세대 버전.

st1(Throughput Optimized HDD)
- HDD 기반, 순차적 처리량(Throughput)이 중요한 워크로드(빅데이터, 로그 처리 등)에 적합.
- 순차 I/O 성능에 초점을 맞춤.
- 임의(Random) I/O에는 적합하지 않음.

sc1(Cold HDD)
- 가장 저렴한 HDD 옵션, 데이터 접근이 매우 드문 워크로드에 적합(아카이빙 등).
- 낮은 IOPS, 낮은 순차 처리량.


여기서 주로 봐야할 점은 각각 성능적인 특징 그리고 ssd와 hdd로 그룹을 나눠서 기억하고
ec2 인스턴스는 ssd 유형의 ebs 볼륨하고만 연결이 가능하다는 점을 추가로 기억하자.

아마 어떤 가상의 상황을 제시하고 어떤 유형을 선택해야 하는지에 대한 문제가 나올 듯 하다 (갑자기..?)

# EBS 다중연결
io1/io2(Provisioned IOPS) 볼륨에서 지원되는 기능으로, 단일 EBS 볼륨을 여러 EC2 인스턴스에 연결할 수 있게 해준다.
클러스팅이나 분산 파일시스템에 적합할 듯 하다.

gp2, gp3에서 안되는 이유는 간단하게 성능 이슈라고 이해하면 되겠다.
다중 인스턴스와 연결되면 iops의 높은 성능이 요구된다.

## 주의점
1. 인스턴스 간 데이터 일관성 관리가 필요하다 일반 파일시스템으로는 동시 기록 시 데이터 손상이 발생할 수 있다고 한다.
따라서, GFS2, 클러스터 파일시스템 등 동시 액세스를 지원하는 파일시스템을 사용하는 것이 일반적이라고 하는데
GFS2, 클러스터 파일시스템 등에 대한 내용은 모르겠다 (당장 시험에 필요한 요소는 아니지만 그래도 나중에 학습하자)

2. 같은 AZ 내에서만 Multi-Attach 가능. (전에 tmi로 설명했다)

# EFS (Elastic File System)
AWS에서 제공하는 완전관리형 NFS(Network File System) 서비스.

## (EFS) NFS 네트워크 파일 시스템이란 무엇인가?
- 네트워크를 통해 여러 컴퓨터가 같은 파일 시스템을 공유할 수 있도록 만든 표준 프로토콜
- 즉 네트워크에 존재하며 여러 인스턴스에서 동시에 접근할 수 있다.

## (EFS) 어떤 장점이 있는가?
- EFS는 리전 단위의 서비스다. 여러 가용영역에서 동시에 접근할 수 있다.
- 각 가용영역에서 자동으로 데이터를 복제하여 높은 가용성을 보장한다. 즉 가용영역 단위로 별도의 스토리지가 존재하며, EFS를 통해 데이터를 서로 동기화하여 여러 가용영역에서 접근할 수 있으며 가용성 또한 유지할 수 있는 것이다.
- 용량을 미리 정의할 필요가 없다.
  - 즉 사용한 용량만큼 지불한다.
  - 파일 시스템 뒤 보이지 않는 곳에 모두가 공유하는 커다란 공용 스토리지가 존재 한다는 것을 유추할 수 있다.

## EFS 스토리지 클래스
- standard
  - 자주 엑세스하는 데이터를 주로 저장하는 계층
  - 빠르고 엑세스 자체의 비용은 없다(다중 가용영역에 복제하여 빠름)
  - 기본 저장에 대한 요금 자체가 다른 계층보다 비쌌던 것으로 기억
-  IA (Infrequent Access)
  - 자주 엑세스하지 않는 데이터를 주로 저장하는 계층
  - 엑세스 자체에 비용 부과 대신 저장에 대한 요금이 저렴
- Archive
  - 1년에 몇 번만 엑세스 하는 경우

특정 계층을 경로로 직접 데이터를 저장할 수는 없다.
기본적으로는 스탠다드 계층에 저장되며 설정한 수명주기 정책에 따라 계층간 데이터 이동이 이루어진다.

스탠다드를 기준으로 다중 가용영역을 활용하여 높은 가용성과 빠른 재해복구가 필요한 운영 환경에서 좋은 선택지. 다만 저렴한 비용으로 개발 환경에서만 활용한다면 아래를 살펴보자

- One Zone
  - 특정 가용영역만 활용한다
  - 엑세스 빈도가 낮은 스토리지 계층을 활용한다.
  - 스탠다드에 비해 47% 가량 저렴하다고 한다

## EFS를 어떻게 활용할 것인가?
전반적으로 올바른 EFS 스토리지 클래스를 활용하면 최대 90%의 비용 절감을 이뤄낼 수 있다고 유데미 dva-c02 강의에선 소개하고 있다.

이 비용 절감이 efs를 쓰기 전과 비교해서인지 무엇인지 기준은 잘 모르겠다.

다만, 계층별로 데이터 저장에 대해 지불하는 요금이 다르니 접근하는 데이터들의 빈도수를 잘 파악한 후 스탠다드 계층에 두고 자주 엑세스 하는 것이 비용적으로 유리한 케이스와 엑세스 자체에 비용을 지불하더라도 그외 계층에 저장해두는 것이 비용적으로 유리한 케이스를 잘 구분해서 이용해야 할 것이다.

그리고 스탠다드가 기본적으로 접근이 빠르니 단순히 efs에 대한 비용만 생각할 것이 아니라 높은 효율성으로 얻을 수 있는 부가적인 비용도 같이 고려하는게 맞다고 생각한다. (그치만 난 그런 판단을 할 수 없다 ㅎ..)

## 그외
실습 영상을 살펴보니 EFS는 vpc 내부에 생성되는걸 확인할 수 있었다.
연결되는 인스턴스들과 동일한 vpc에 속해있어 aws 내부 백본망을 통해 빠르게 통신할 수 있는 것으로 보인다.
(vpc로 하나의 논리적 네트워크 영역 안에서는 서로 다른 가용 영역도 백본을 활용해 빠르게 통신할 수 있다 vpc 외부에 생성되는 ebs와의 차이가 이것이다.)
