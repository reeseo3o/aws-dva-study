# EC2란?
Elastic Compute Cloud의 줄임말로 아마존이 사용자에게 임대해주는 가상의 컴퓨터 자원이라고 할 수 있다

아마존은 실제로 본인들의 데이터 센터에 물리적인 머신들을 구축한 후 사용자로부터 ec2 인스턴스 생성 요청이 들어오면
요청 내용을 기반으로 물리머신 내의 자원을 가상화하여 가상머신을 생성하여 유저에게 제공한다.

<br>

# EC2의 이점
- 물리적인 컴퓨터 자원을 직접 관리할 필요가 없다.
- 필요한 자원만큼 구성하여 사용한 만큼 돈을 지불할 수 있으며 상황에 따라 자원(cpu, 메모리)을 조절할 수 있다.

이 외에도 필요한 환경 예를들면 특정 os의 컴퓨터라던가 필요한 자원에 맞게 사용할 수 있고 이래저래 편하다!

# 구성요소
- ami: 아마존 머신 이미지의 약자. EC2 인스턴스를 실행하기 위한 템플릿이다.
조금 더 쉽게 말하면 컴퓨터가 기본적인 동작을 할 수 있으려면 최소한의 구성 요소들이 필요할텐데 이 구성 요소를 미리 템플릿으로 만들어놓고 이 이미지를 기반으로 가상머신을 만드는 것이다.

보통 콘솔 상에서 ec2를 생성할 때 퀵 스타트에 보여지는 ami들은 정말 최소한의 세팅 정보만 담겨있고
os, 아키텍처, 가상화 방식, 루트 디바이스 유형(보통 ebs)에 대한 정보가 담겨있다.

만약 회사나 뭐 특정 이러저러한 이유에 의거하여... 특정 정해진 스펙의 컴퓨팅 자원을 자주 생성해서 써야된다면

ami를 커스터마이징 해서 스냅샷 형태로 저장 후 활용하는 방안이 있다.

이 안엔 데이터베이스, 네트워크 설정, 서버 애플리케이션 설치뿐만 아니라 상용 가능한 서비스 코드를 담은 상태로도 ami를 만들어 낼 수 있다.

ami를 이정도로 깊게 커스텀해서 쓰는 경우가 실제로 있을까 궁금하긴 하다. 개인적으로 잘 납득은 안가지만
예상치 못한 재해로 인해 서버 장애가 발생할 경우 빠른 복구를 위해 좋을 것 같다는 생각은 든다.
(적어도 도커의 소프트웨어 수준 가상화에 비해선 모든 구성을 다 담고있으니 빠르게 복구가 가능하지 않을까..는 무슨 앞으로 배울 aws의 다양한 기능을 활용하면 이것도 필요 없겠쥬~ )

그리고 ami에 별 세팅 정보를 다 넣을 수 있는데 cpu와 메모리를 미리 지정할 순 없다.

ami는 운영체제, 소프트웨어 수준의 스펙을 구성하고 실제 하드웨어 스펙은 인스턴스 유형으로 분리해서 관리한다거나
표준화된 ami로 다양한 인스턴스 유형으로 확장, 축소하기 위함이라는데

사실 내 눈엔 그저 인스턴스 유형으로 과금을 멕여야 하기 때문에 하드웨어 자원에 대한 스펙 정의는 못하게 하는 걸로만 보인다ㅎ

- 루트 디바이스
ami를 설명하면서 잠깐 언급했던 내용.
ami를 기반으로 운영체제, 소프트웨어 자원을 가상화하여 제공받고 인스턴스 유형을 통해 cpu, 메모리를 가상화하여 제공받는다.

그렇다면 실제 데이터를 저장해야하는 하드디스크의 역할은 누가 하는가? 루트 디바이스가 한다.
보통은 ec2를 생성할 때 루트 디바이스가 ebs로 지정되며 우리가 ssh를 통해 접속해서 ec2에 저장하는 모든 파일 등의 데이터는 실제론 이 루트 디바이스에 저장된다.

이 ebs는 추후 다른 섹션에서 더 자세히 다루고 있지만 ec2가 존재하는 실제 머신에 물리적으로 연결된 것은 아니다.
별도로 다른 곳에 물리적으로 존재하며 ec2와 네트워크 통신으로 연결된 상태이다.


음 이 외에 ec2에 대해서는 무엇을 더 말해야 할 지 모르겠다! 끝!
