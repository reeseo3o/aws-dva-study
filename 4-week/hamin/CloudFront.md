# CloudFront

Amazon CloudFront는 .html, .css, .js 및 이미지 파일과 같은 정적 및 동적 웹 콘텐츠를 사용자에게 더 빨리 배포하도록 지원하는 웹 서비스입니다.

CloudFront는 엣지 로케이션이라고 하는 데이터 센터의 전 세계 네트워크를 통해 콘텐츠를 제공합니다. CloudFront를 통해 서비스하는 콘텐츠를 사용자가 요청하면 지연 시간이 가장 낮은 엣지 로케이션으로 요청이 라우팅되므로 가능한 최고의 성능으로 콘텐츠가 제공됩니다.

→ 정적 및 동적 웹 콘텐츠를 빠르게 배포하도록 지원한다.

→ 엣지 로케이션에서 응답 데이터를 캐싱해둔다.

→ 사용자가 동일 데이터를 요청할 경우 가장 지연시간이 낮은 엣지 로케이션이 캐싱해둔 데이터를 반환한다.

<br>

## 캐싱 및 캐싱 정책

기본적인 캐싱 사이클

엣지 서버의 캐싱 유무에 따라 갖고 있는 콘텐츠를 제공하는지 또는 새 버전(latest)의 콘텐츠를 엣지 서버에 적재 후 사용자에게 콘텐츠를 제공하는 방식으로 돌아갑니다.

다만, 컨텐츠를 어떤 조건으로 어떻게 얼마만큼 캐싱해야 될 지는 상황에 따라 다를 수 있습니다.

따라서 다양한 캐싱 정책을 상황에 맞게 설정하는게 중요합니다.

### 캐싱 정책

- **TTL (Time-to-Live) 설정**
- **Cache-Control 헤더와의 연계**
- **캐시 키** 설정
- **Query String, 헤더, 쿠키 처리**

<br>

### TTL 설정
TTL은 CloudFront가 객체를 캐시하는 시간을 설정합니다. 이 시간 동안은 다시 원본 서버에 요청을 보내지 않고 캐시에서 콘텐츠를 제공합니다. TTL은 초 단위로 설정됩니다.

종류:
Minimum TTL: CloudFront가 콘텐츠를 최소한으로 캐시하는 시간. 이 값을 설정하면 그 이하의 TTL을 갖는 객체는 이 값을 따르게 됩니다.

Maximum TTL: 객체가 캐시될 수 있는 최대 시간을 설정합니다. 만약 원본 서버가 TTL을 지정하지 않으면, 이 값이 기본적으로 적용됩니다.

Default TTL: 원본에서 TTL이 설정되지 않은 경우에 사용되는 기본 TTL입니다.

동작 예시:
Maximum TTL이 1시간으로 설정되어 있다면, CloudFront는 객체를 최대 1시간 동안만 캐시하고, 그 시간이 지나면 다시 원본 서버에서 최신 콘텐츠를 가져옵니다.

<br>

### Cache-Control 헤더와의 연계
Cache-Control 헤더는 웹 서버(예: S3, EC2 등)에서 콘텐츠의 캐시 정책을 지정하는 HTTP 헤더입니다. CloudFront는 이 헤더를 받아 객체를 어떻게 캐시할지 결정합니다.

주요 Cache-Control 지시자:
max-age: 객체가 캐시될 수 있는 시간을 지정합니다.

예: Cache-Control: max-age=3600 (1시간 동안 캐시)

no-cache: 객체를 캐시하지 않음, 항상 원본에서 새로 가져옴

no-store: 요청 및 응답에 캐시하지 않음

public: 모든 캐시 서버에 객체를 저장할 수 있음을 명시

private: 사용자 개인 캐시에서만 저장 가능

동작 예시:
원본 서버에서 Cache-Control: max-age=300을 설정하면, CloudFront는 이 콘텐츠를 5분 동안 캐시하고, 5분이 지나면 원본 서버에 요청을 보냅니다.

<br>

### 캐시 키(Cache Key)
캐시 키는 CloudFront가 콘텐츠를 어떤 기준으로 캐시할지 결정하는 요소입니다. 캐시 키는 URL, Query String, 헤더, 쿠키 등을 기준으로 다르게 설정할 수 있습니다.

캐시 키의 주요 구성 요소:
URL: 기본적으로 CloudFront는 요청 URL을 캐시 키로 사용합니다.

Query String: 쿼리 문자열을 캐시 키에 포함시킬지 여부를 결정합니다. 예를 들어, ?size=large와 같은 쿼리 문자열이 다를 경우 캐시가 분리될 수 있습니다.

Headers: 헤더 값에 따라 캐시를 다르게 적용할 수 있습니다. 예를 들어, Accept-Language 헤더를 기준으로 캐시를 다르게 설정할 수 있습니다.

Cookies: 쿠키가 포함된 요청의 경우, 쿠키를 기준으로 캐시를 다르게 할 수 있습니다.

동작 예시:
Query String을 사용하여 캐시를 다르게 할 수 있습니다. 예를 들어, ?size=small과 ?size=large는 다른 콘텐츠로 취급되어 각각 캐시됩니다.

<br>

### Query String, 헤더, 쿠키 처리

Query String 처리
CloudFront는 기본적으로 쿼리 문자열을 무시할 수 있습니다. 이를 활성화하면 쿼리 문자열이 달라질 때마다 별도의 캐시를 생성할 수 있습니다.

Query String Forwarding and Caching:

None: 쿼리 문자열을 무시하고 URL만으로 캐시합니다.

Forward all, cache based on all: 모든 쿼리 문자열을 캐시 키에 포함시켜 다르게 처리합니다.

Forward specific: 특정 쿼리 문자열만 캐시 키에 포함시킵니다.

헤더 처리
CloudFront는 특정 HTTP 헤더를 캐시 키에 포함시켜 다르게 처리할 수 있습니다. 예를 들어, Accept-Encoding, User-Agent 헤더 등을 기준으로 캐시를 다르게 할 수 있습니다.

쿠키 처리
CloudFront는 쿠키가 포함된 요청에 대해서도 캐시 키를 다르게 처리할 수 있습니다. 특정 쿠키 값을 기준으로 캐시를 분리하여 제공할 수 있습니다.

<br>

## 캐시 무효화 (Cache Invalidation)

캐시 무효화는 CloudFront의 엣지 로케이션에 저장된 콘텐츠를 강제로 제거하고, 다음 요청 시 원본 서버에서 최신 콘텐츠를 가져오도록 하는 기능입니다.

### 캐시 무효화가 필요한 상황

- 원본 서버의 콘텐츠가 업데이트되었으나 TTL이 만료되지 않은 경우
- 긴급하게 잘못된 콘텐츠를 제거해야 하는 경우
- 캐시된 콘텐츠에 오류가 있는 경우

### 캐시 무효화 방법

1. **특정 파일 무효화**
   - 개별 파일 경로를 지정하여 무효화: `/images/logo.png`
   - 와일드카드를 사용한 무효화: `/images/*`

2. **전체 배포 무효화**
   - 모든 파일을 무효화: `/*`
   - 주의: 전체 무효화는 비용이 많이 들 수 있음

### 무효화 비용 및 제한

- 매월 무료 무효화 할당량이 있음 (일반적으로 월 1,000개 경로)
- 할당량 초과 시 추가 비용 발생
- 동시에 진행할 수 있는 무효화 요청의 수에 제한이 있음

### 무효화 대안

- **버전이 지정된 객체 이름 사용**: `/images/logo.png?v=2`
- **객체 버전 관리**: `/images/logo-v2.png`
- 이러한 방법은 무효화 없이 새 콘텐츠를 제공할 수 있음

<br>

## 캐시 동작 (Cache Behaviors)

캐시 동작은 CloudFront 배포의 다양한 URL 패턴에 대해 서로 다른 캐싱 설정을 적용할 수 있는 기능입니다.

### 캐시 동작의 주요 구성 요소

1. **경로 패턴 (Path Pattern)**
   - 특정 URL 패턴에 대한 설정 적용
   - 예: `/images/*`, `/api/*`, `*.jpg`
   - 기본 캐시 동작(Default Cache Behavior)은 `/*`로 설정됨

2. **원본 설정 (Origin Settings)**
   - 각 경로 패턴별로 다른 원본 서버 지정 가능
   - S3 버킷, EC2 인스턴스, 로드 밸런서 등 다양한 원본 지정 가능

3. **뷰어 프로토콜 정책 (Viewer Protocol Policy)**
   - HTTP to HTTPS 리디렉션
   - HTTPS만 허용
   - HTTP와 HTTPS 모두 허용

4. **허용된 HTTP 메서드 (Allowed HTTP Methods)**
   - GET, HEAD만 허용
   - GET, HEAD, OPTIONS 허용
   - 모든 HTTP 메서드 허용 (PUT, POST, PATCH, DELETE 포함)

### 캐시 동작 활용 예시

1. **정적 콘텐츠와 동적 콘텐츠의 분리**
   - 정적 콘텐츠(`/static/*`): 긴 TTL, 쿼리 문자열 무시
   - 동적 콘텐츠(`/api/*`): 짧은 TTL, 모든 쿼리 문자열 및 헤더 포함

2. **이미지와 API 요청의 분리**
   - 이미지(`/images/*`): S3 원본, 장기 캐싱
   - API(`/api/*`): 로드 밸런서 원본, 짧은 캐싱 또는 캐싱 없음

3. **사용자 인증이 필요한 콘텐츠 처리**
   - 인증 필요 경로(`/secure/*`): 쿠키 전달, 특정 헤더 포함
   - 공개 콘텐츠(`/public/*`): 쿠키 및 헤더 무시

### 캐시 동작 우선순위

- 여러 캐시 동작이 중첩될 경우, 가장 구체적인 경로 패턴이 우선 적용됨
- 예: `/images/thumbnails/*`는 `/images/*`보다 우선순위가 높음
- 기본 캐시 동작은 다른 패턴이 일치하지 않을 때 적용됨

## CloudFront - 오리진으로서의 ALB

Application Load Balancer(ALB)는 CloudFront의 오리진 서버로 사용될 수 있으며, 이는 동적 콘텐츠 처리와 서버 로드 분산에 매우 효과적인 조합입니다.

### ALB를 오리진으로 사용하는 이유

- **로드 밸런싱**: 백엔드 서버 간에 트래픽을 분산하여 고가용성 확보
- **헬스 체크**: 비정상 서버를 자동으로 감지하고 트래픽 우회
- **경로 기반 라우팅**: 요청 URL 경로에 따라 다른 대상 그룹으로 라우팅
- **SSL 종료**: SSL/TLS 처리를 ALB에서 수행하여 백엔드 서버 부하 감소

### 설정 방법

1. **오리진 도메인**: ALB의 DNS 이름 사용 (예: `my-alb-1234567890.us-east-1.elb.amazonaws.com`)
2. **오리진 프로토콜 정책**:
   - HTTP Only: CloudFront에서 ALB로 HTTP만 사용
   - HTTPS Only: CloudFront에서 ALB로 HTTPS만 사용
   - Match Viewer: 최종 사용자의 요청 프로토콜과 일치
3. **오리진 경로**: 모든 요청에 추가할 경로 접두사 (선택 사항)

### 주요 고려사항

- **보안 그룹**: ALB의 보안 그룹은 CloudFront의 IP 범위에서 오는 트래픽만 허용하도록 설정
- **헤더 전달**: CloudFront에서 ALB로 필요한 헤더가 전달되도록 설정 (예: `Host` 헤더)
- **쿠키 및 쿼리 문자열**: 세션 관리나 동적 콘텐츠에 필요한 쿠키와 쿼리 문자열 전달 설정
- **캐시 TTL**: 동적 콘텐츠의 경우 적절한 TTL 설정 필요

<br>

## CloudFront - 지리적 제한

지리적 제한(Geo Restriction)은 사용자의 지리적 위치에 따라 CloudFront 콘텐츠에 대한 접근을 제어하는 기능입니다.

### 기본 개념

- **허용 목록(Whitelist)**: 특정 국가에서만 콘텐츠에 접근 허용
- **차단 목록(Blacklist)**: 특정 국가에서 콘텐츠 접근 차단
- **위치 확인**: 사용자의 IP 주소를 기반으로 위치 확인

### 설정 방법

1. CloudFront 배포 설정에서 "제한" 탭 선택
2. 지리적 제한 활성화
3. 제한 유형 선택:
   - 허용 목록: 접근을 허용할 국가 선택
   - 차단 목록: 접근을 차단할 국가 선택
4. 접근이 제한된 사용자에게 표시할 오류 메시지 사용자 정의 (선택 사항)

### 주요 사용 사례

- **라이센스 제한**: 특정 지역에서만 사용 가능한 콘텐츠(영화, 음악 등) 제한
- **규제 준수**: 특정 국가의 법적 규제를 준수하기 위한 접근 제한
- **지역별 콘텐츠**: 특정 지역 사용자만 볼 수 있는 콘텐츠 제공

### 한계점

- **국가 수준 제한**: 도시나 지역 단위가 아닌 국가 단위로만 제한 가능
- **VPN/프록시 우회**: 사용자가 VPN이나 프록시를 사용하여 제한을 우회할 가능성 있음
- **정확도**: IP 기반 지리적 위치 확인의 정확도 제한
