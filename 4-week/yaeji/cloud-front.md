## CloudFront란?
CloudFront는 AWS의 **콘텐츠 전송 네트워크(CDN)**입니다. 시험에서 CDN 관련 내용이 나오면 가장 먼저 CloudFront를 떠올리면 됩니다. CloudFront는 전 세계의 **엣지 로케이션(POP, Point of Presence)**에 콘텐츠를 캐시함으로써, 사용자 요청을 오리진까지 전달하지 않고 빠르게 응답할 수 있도록 해줍니다.

## CloudFront의 주요 이점
- **저지연 콘텐츠 제공**: 사용자의 지리적 위치에서 가장 가까운 엣지 로케이션에서 콘텐츠 제공
- **글로벌 커버리지**: 약 216개의 POP(AWS 엣지 로케이션) 보유
- **성능 향상**: 반복 요청은 캐시에서 제공되므로 웹사이트 응답 속도 개선
- **보안 내장**: DDoS 대응을 위한 AWS Shield, 애플리케이션 계층 보안을 위한 AWS WAF와 통합

## 예시 시나리오
- **S3 버킷이 오스트레일리아에 있음**
- 사용자는 미국에서 해당 콘텐츠를 요청함
- 처음 요청 시 CloudFront가 오스트레일리아에서 콘텐츠를 가져와 미국 엣지 로케이션에 캐시
- 이후 동일한 요청은 미국에서 바로 응답 가능 → 빠르고 효율적인 전달

## CloudFront의 오리진
CloudFront는 다음과 같은 오리진과 연동할 수 있습니다:
- **Amazon S3**: 가장 일반적인 정적 콘텐츠 오리진
- **S3 웹사이트 엔드포인트**: Static Website Hosting 기능을 활성화한 S3 버킷
- **Application Load Balancer (ALB)**: 동적 콘텐츠 처리에 적합
- **Amazon EC2**: 직접 HTTP 서버 운영 시 사용 가능
- **기타 HTTP 백엔드**: 외부 API, 서드파티 웹 서버 등

## 오리진 보안: OAC
**Origin Access Control (OAC)**를 사용해 CloudFront만 S3 버킷에 접근할 수 있도록 설정합니다. 이는 기존의 **OAI(Origin Access Identity)**를 대체하는 최신 보안 방식입니다.

## CloudFront 동작 흐름
1. 사용자가 엣지 로케이션에 요청을 보냄
2. 엣지 로케이션에 캐시된 콘텐츠가 있으면 즉시 응답
3. 없을 경우 → **오리진(S3, EC2 등)**에 요청 전송
4. 받아온 콘텐츠를 로컬 캐시에 저장하고 응답
5. 이후 동일한 요청은 캐시에서 빠르게 처리

## 엣지 로케이션 & 보안 구성
엣지 로케이션은 프라이빗 네트워크를 통해 오리진(S3 등)과 연결됩니다. 예를 들어, 미국 LA, 브라질 상파울루 등에서 사용자 요청이 발생하면 해당 지역 엣지 로케이션이 응답하고, 프라이빗 링크로 오리진에 연결해 콘텐츠를 확보합니다.

## CloudFront vs. S3 리전 간 복제
| 항목 | CloudFront | S3 리전 간 복제 |
|:---:|:---:|:---:|
| 목적 | 전 세계 사용자 대상 콘텐츠 캐시 제공 (CDN) | 리전 간 전체 복제 (백업, 가용성) |
| 방식 | 엣지 로케이션에 콘텐츠 캐시 | 지정된 리전에 버킷 복제 |
| 캐시 처리 | 있음 (TTL 설정) | 없음 (실시간 복제) |
| 적합한 콘텐츠 | 정적 콘텐츠 | 동적/실시간 변경 콘텐츠 |
| 스토리지 비용 | 원본만 저장 (엣지는 일시적 캐시) | 복제 리전마다 저장 (비용 증가) |

CloudFront는 읽기 최적화 CDN, S3 복제는 쓰기 동기화용 데이터 복제라고 보면 됩니다.

## CloudFront 캐시 동작 원리와 정책 정리
### CloudFront 캐시의 기본 원리
CloudFront는 엣지 로케이션(POP)마다 별도의 캐시 저장소를 운영합니다. 즉, 엣지 로케이션 수만큼 캐시가 생성되며, 사용자의 요청은 가장 가까운 엣지에서 처리됩니다.

### 캐시 처리 흐름
1. 사용자가 CloudFront를 통해 콘텐츠 요청
2. 엣지 로케이션에서 캐시에 콘텐츠가 있는지 확인
   - ✔️ 캐시 있음 → 바로 응답
   - ❌ 캐시 없음 → 오리진에 요청 후 응답 받아 캐시 저장
3. 이후 동일한 콘텐츠 요청 시 엣지에서 바로 제공

오리진 요청을 최소화하고, **캐시 적중률(Cache Hit Ratio)**을 높이는 것이 핵심입니다.

### 캐시 키(Cache Key)
캐시 키는 캐시 내 객체를 고유하게 식별하는 ID입니다. 기본적으로 캐시 키는 다음으로 구성됩니다:
- `<호스트 이름> + <리소스 경로>`

#### 예시
- 요청: `GET https://mywebsite.com/content/stories/example-story.html`
- 캐시 키: `mywebsite.com + /content/stories/example-story.html`

### 캐시 정책(Cache Policy)
CloudFront는 콘텐츠를 얼마나 세부적으로 캐시할지 결정하기 위해 캐시 키를 커스터마이징할 수 있게 합니다. 사용자별, 기기별, 언어별 등 다양한 요청 변형에 따라 캐시 키를 구성할 수 있습니다.

### 캐시 키에 포함할 수 있는 요소들
- **HTTP 헤더**: 예: Accept-Language, User-Agent
- **쿠키**: 사용자 세션 등 다양한 상태 추적
- **쿼리 문자열**: URL의 ? 뒤 매개변수

### 캐시 정책 설정 옵션
- **HTTP 헤더**
  - None: 헤더를 캐시 키에 포함하지 않음 (기본, 성능 우수)
  - Whitelist: 특정 헤더만 포함
  - Include All-Except: 지정한 것 제외하고 모두 포함
  - All: 모든 헤더 포함 (성능 저하 위험)

- **쿠키 / 쿼리 문자열**
  - 동일한 옵션 제공: None, Whitelist, Include All-Except, All

포함 항목이 많을수록 캐시 키가 세분화되며, 캐시 적중률은 낮아질 수 있습니다.

### TTL 설정
캐시 보관 기간(Time To Live)은 캐시 정책에서 설정할 수 있습니다. 0초 ~ 1년까지 지정 가능하며, 오리진에서 Cache-Control, Expires 헤더로 TTL을 직접 지정할 수도 있습니다.

### 오리진 요청 정책 (Origin Request Policy)
오리진 요청 정책은 오리진으로 어떤 정보를 전달할지 결정합니다.

#### 핵심 차이점
| 구분 | 캐시 정책(Cache Policy) | 오리진 요청 정책(Origin Request Policy) |
|:---:|:---:|:---:|
| 목적 | 어떤 요청을 캐시로 식별할지 결정 | 오리진에 어떤 정보를 보낼지 결정 |
| 영향 대상 | 캐시 적중률, 캐시 구조 | 오리진 동작, 요청 처리 결과 |
| 공통 설정 요소 | 헤더, 쿠키, 쿼리 문자열 | 동일하나, 캐시에 영향 없음 |

오리진 요청에 포함할 수 있는 항목은 요청에 존재하는 헤더, 쿠키, 쿼리 문자열이며, 뷰어 요청에 존재하지 않는 정보도 추가 가능 (예: API 키, 사용자 정의 헤더).

#### 예를 들어
Authorization, Session-ID 등의 민감 정보를 오리진에 전달하지만 캐시 키에는 포함하지 않도록 설정할 수 있습니다.

### 예시 시나리오 요약
- **캐시 키에 포함되는 정보**: 호스트 이름 + 리소스 경로 + Authorization 헤더
- **오리진 요청에 추가적으로 포함되는 정보**: User-Agent + Session-ID + 특정 쿼리 문자열

이렇게 하면 캐시는 덜 세분화되어 적중률이 높아지고, 오리진에는 필요한 정보가 모두 전달됩니다.

### 최종 정리
| 항목 | 설명 |
|:---:|:---:|
| 캐시 키 | 캐시에서 객체를 식별하는 고유 키 (기본: 호스트 + 경로) |
| 캐시 정책 | 어떤 요소를 캐시 키로 사용할지 설정 (헤더/쿠키/쿼리) |
| TTL 설정 | 캐시 만료 시간 지정 (0초 ~ 1년, 또는 Cache-Control 사용) |
| 오리진 요청 정책 | 오리진에 어떤 추가 데이터를 보낼지 정의 |
| 성능 최적화 팁 | 캐시 키는 단순하게, 오리진 요청은 필요 정보만 전달하기 |

## CloudFront 캐시 무효화 & 경로 기반 캐시 동작
### CloudFront 캐시 무효화(Invalidation)
CloudFront는 콘텐츠를 **각 엣지 로케이션(POP)**의 캐시에 저장합니다. 그러나 백엔드 오리진의 콘텐츠가 변경되었을 때, 엣지 로케이션은 이를 인지하지 못합니다.

#### 문제점
오리진의 콘텐츠를 업데이트해도 **TTL(Time-To-Live)**이 만료되기 전까지는 엣지에서 이전 콘텐츠를 계속 제공하게 됩니다. 이는 사용자에게 오래된 콘텐츠를 제공할 수 있는 위험이 있습니다.

#### 해결 방법: 캐시 무효화(Invalidation)
CloudFront는 캐시 무효화 요청을 통해 TTL과 관계없이 캐시된 객체를 즉시 삭제할 수 있습니다.

#### 무효화 방식
- 특정 파일: `/index.html`
- 경로 전체: `/images/*` → 와일드카드(*)를 사용해 경로 단위로 무효화 가능

#### 동작 예시
CloudFront 배포에 엣지 로케이션 2개가 있고, `/index.html`과 `/images/*`가 캐시되어 있음. S3에서 콘텐츠를 업데이트한 후:
- `/index.html` 무효화
- `/images/*` 무효화

CloudFront는 엣지 로케이션 캐시에서 해당 콘텐츠를 제거. 다음 사용자 요청 시:
- 엣지에 캐시 없음 → 오리진에서 최신 콘텐츠 가져옴 → 캐시에 다시 저장

### 경로 기반 캐시 동작 (Cache Behaviors by Path)
CloudFront에서는 URL 경로에 따라 다른 오리진과 다른 캐시 정책을 적용할 수 있습니다.

#### 예시 설정
| 경로 패턴 | 오리진 | 설명 |
|:---:|:---:|:---:|
| /api/* | ALB (동적 서버) | REST API 등 동적 콘텐츠 처리 |
| /images/* | S3 버킷 | 정적 이미지 제공 |
| /* (기본값) | S3 또는 기본 오리진 | 그 외 요청 처리용 |

가장 구체적인 경로가 우선 적용되며, 일치하는 경로가 없으면 /* 기본 동작이 사용됩니다.

### 경로 기반 인증 예시
- 로그인 기반 접근 제어 구성
- /login 경로에 별도 캐시 동작을 설정하여 EC2 인스턴스로 리디렉션
- EC2 인스턴스가 CloudFront 서명된 쿠키 생성 및 클라이언트에 전달
- 사용자는 이 쿠키로 /login이 아닌 리소스에 접근
- 기본 캐시 동작(/*)에는 서명된 쿠키가 있을 때만 접근 허용하도록 설정
- 사용자가 로그인하지 않은 경우 /login 경로로 리디렉션하여 보안 강화

### 캐시 적중률 향상 전략
#### 정적 콘텐츠 vs 동적 콘텐츠
| 콘텐츠 유형 | 오리진 예시 | 캐시 정책 |
|:---:|:---:|:---:|
| 정적 콘텐츠 | Amazon S3 | 헤더/쿠키 포함하지 않음 (단순 캐시 키) |
| 동적 콘텐츠 | EC2, ALB, API 서버 | 헤더, 쿠키, 쿼리 문자열을 활용한 세분화된 캐시 키 사용 |

정적 리소스는 가능한 한 단순하게 구성하여 캐시 적중률을 극대화하고, 동적 콘텐츠는 필요한 조건을 기준으로 세분화하여 정확한 사용자 맞춤 응답을 제공합니다.

### 요약
| 항목 | 설명 |
|:---:|:---:|
| 캐시 무효화 | TTL 이전이라도 캐시된 객체를 수동으로 제거 |
| 와일드카드 지원 | /images/*와 같이 경로 전체 무효화 가능 |
| 경로 기반 캐시 동작 | 경로에 따라 오리진 및 캐시 정책 분기 설정 |
| 정적 vs 동적 처리 구분 | 정적은 단순화, 동적은 세분화로 캐시 효율 관리 |
| 서명된 쿠키 인증 처리 | 로그인 인증과 함께 CloudFront 접근 제어 구성 가능 |

CloudFront의 정교한 캐시 제어와 경로 기반 동작을 잘 활용하면 웹 애플리케이션의 성능과 보안을 동시에 향상시킬 수 있습니다.

## CloudFront 오리진: EC2 & ALB
CloudFront는 퍼블릭 콘텐츠 캐싱뿐 아니라, **EC2 인스턴스나 ALB(Application Load Balancer)**와 같은 HTTP 백엔드 오리진에도 연결할 수 있습니다. 사용자 요청은 **CloudFront 엣지 로케이션(POP)**에서 처리되어 해당 오리진으로 전달됩니다.

### 패턴 1: EC2 인스턴스를 오리진으로 사용하는 경우
#### 구성 시나리오
- EC2 인스턴스에서 HTTP 웹 애플리케이션을 직접 실행
- 사용자 요청이 CloudFront 엣지 로케이션 → EC2 인스턴스로 전달됨

#### 필수 조건
| 항목 | 설명 |
|:---:|:---:|
| EC2 인스턴스 | 퍼블릭 액세스 가능해야 함 (공용 IP 또는 ALB 필요) |
| 보안 그룹 설정 | CloudFront 엣지 로케이션의 퍼블릭 IP를 허용해야 함 |
| CloudFront IP 목록 | 공식 AWS 문서에서 확인 가능: AWS IP 주소 JSON 또는 AWS 공식 가이드 참조 |

CloudFront는 VPC 내부 프라이빗 연결을 지원하지 않으므로, 엣지 로케이션에서 EC2로 접근하려면 퍼블릭 네트워크 상에 노출되어야 합니다.

### 패턴 2: ALB를 오리진으로 사용하는 경우
#### 구성 시나리오
- 퍼블릭 액세스 가능한 ALB를 CloudFront 오리진으로 지정
- ALB는 백엔드 EC2 인스턴스와 프라이빗 VPC 연결을 통해 통신

#### 필수 조건
| 항목 | 설명 |
|:---:|:---:|
| ALB | 퍼블릭 액세스 가능 (퍼블릭 서브넷에 배포) |
| EC2 인스턴스 | 퍼블릭이 아닌 프라이빗 인스턴스 가능 |
| 보안 그룹 설정 | EC2의 보안 그룹에서 ALB의 보안 그룹을 허용해야 함 |
| CloudFront ↔ ALB | ALB 보안 그룹에서 CloudFront 퍼블릭 IP를 허용해야 함 |

ALB를 통해 EC2 인스턴스를 직접 공개하지 않아도 되므로, 보안성이 더 높고 관리가 수월합니다.

### 패턴 비교 정리
| 항목 | EC2 직접 연결 | ALB 연결 |
|:---:|:---:|:---:|
| CloudFront 연결 | 엣지 → EC2 | 엣지 → ALB → EC2 |
| EC2 노출 방식 | 퍼블릭 IP 필요 | 프라이빗 가능 |
| 보안 그룹 설정 | EC2에서 CloudFront IP 허용 | ALB: CloudFront IP 허용, EC2: ALB 보안 그룹 허용 |
| 보안성 | 상대적으로 낮음 | 상대적으로 높음 |
| 권장 여부 | 테스트 환경 또는 소규모 시스템 | 프로덕션 환경에 권장 |

#### 참고: CloudFront 퍼블릭 IP 목록 확인
AWS는 CloudFront 엣지 로케이션의 IP 주소 범위를 JSON으로 제공합니다:
- URL: https://ip-ranges.amazonaws.com/ip-ranges.json
- CloudFront 전용 IP 찾기: "service": "CLOUDFRONT" 키워드로 검색

이 IP 범위를 보안 그룹의 소스로 등록하면 CloudFront 엣지 요청을 허용할 수 있습니다.

## CloudFront 고급 기능 정리 (시험 대비용)
### 요금 및 가격 등급 (Price Classes)
#### 기본 개념
CloudFront는 전 세계 엣지 로케이션을 통해 콘텐츠를 제공하며, 위치에 따라 전송 요금이 다릅니다.

예:
- 미국/캐나다/멕시코 → 1GB당 $0.085 (10TB 이하 기준)
- 인도 → 1GB당 $0.17

전송량이 많아질수록 단가 감소
- 예: 5PB 전송 시, 미국 기준 1GB당 $0.02

#### 가격 등급 (Price Class)
CloudFront 배포 시 요금 절감을 위해 사용할 엣지 로케이션을 제한할 수 있습니다.

| Price Class | 사용 지역 | 특징 |
|:---:|:---:|:---:|
| All | 전 세계 | 성능 최상, 비용 높음 |
| 200 | 북미, 유럽, 아시아 일부 | 성능/비용 균형 |
| 100 | 북미, 유럽 | 가장 저렴, 엣지 수 제한 |

### 다중 오리진(Multiple Origins) & 경로 기반 라우팅
#### 개념
경로에 따라 서로 다른 오리진으로 요청을 라우팅 가능

#### 예시
| 경로 | 오리진 |
|:---:|:---:|
| /api/* | ALB (동적 콘텐츠) |
| /* | S3 (정적 콘텐츠) |

각 경로에 대해 별도의 캐시 정책, TTL, 보안 설정을 적용 가능

### 오리진 그룹 (Origin Groups)
#### 개념
**장애 조치(Failover)**를 위한 주 오리진 + 보조 오리진 구성

주 오리진 장애 시, CloudFront가 보조 오리진으로 요청 재전송

#### 예시
| 오리진 그룹 구성 | 설명 |
|:---:|:---:|
| A: S3 (서울 리전) | 주 오리진 |
| B: S3 (도쿄 리전) | 보조 오리진 (복제 대상) |

리전 간 S3 복제를 이용해 콘텐츠 일관성 확보
재해 복구 DR 구성 가능

### 필드 수준 암호화 (Field-Level Encryption)
#### 목적
HTTPS 인플라이트 암호화 외에, 특정 민감 정보 필드를 추가로 암호화

#### 작동 방식
- 클라이언트 → HTTPS로 CloudFront에 요청
- 엣지 로케이션이 지정된 필드를 공용키로 암호화
- 암호화된 정보는 오리진(웹 서버)까지 전달
- 웹 서버만 개인 키를 통해 해당 필드 해독 가능

#### 특징
- 최대 10개 필드 지정 가능
- 예시: 신용카드 번호, 주민번호 등
- 중간 경로 (CloudFront, ALB)는 내용 해독 불가 → 데이터 보호 강화

### 요약 정리
| 항목 | 설명 |
|:---:|:---:|
| Price Class | 사용 엣지 로케이션 제한으로 비용 절감 (100/200/All) |
| 다중 오리진 | 경로 별로 오리진 라우팅 가능 (/api, /* 등) |
| 오리진 그룹 | 고가용성 구성 (장애 시 자동 Failover) |
| 필드 수준 암호화 | 엣지 레벨에서 민감 필드 암호화 (공용키 사용) |
| 실전 팁 | ALB와 S3 오리진을 조합하면 안정성과 확장성 ↑ |

## CloudFront 실시간 로그 & Kinesis 연동
### 개요
Amazon CloudFront는 수신한 모든 요청에 대한 실시간 로그 데이터를 Kinesis 데이터 스트림으로 전송할 수 있습니다. 이를 통해 콘텐츠 요청에 대한 실시간 모니터링, 분석, 자동 대응이 가능합니다.

### 구성 흐름
```mermaid
graph LR
A[CloudFront] --> B[Kinesis Data Stream]
B --> C[Lambda 함수 (실시간 처리)]
B --> D[Kinesis Firehose (배치 처리)]
D --> E[S3 / OpenSearch / 기타 대상]
```

### 주요 구성 요소
| 구성 요소 | 설명 |
|:---:|:---:|
| CloudFront | 요청 발생 지점, 실시간 로그 활성화 가능 |
| Kinesis Data Stream | 실시간 로그가 전송되는 스트림 |
| Lambda 함수 | 실시간 분석/필터링/알림 처리 가능 |
| Kinesis Data Firehose | 로그 데이터를 S3, OpenSearch 등으로 배치 전송 |
| S3/OpenSearch 등 | 최종 로그 저장 또는 분석 대상 시스템 |

### 실시간 로그 설정 옵션
#### 샘플링 비율 설정
모든 요청을 로그에 포함할 수도 있고, **특정 비율(예: 10%, 1%)**만 수집해 성능/비용 균형 유지 가능

#### 경로 기반 수집 (캐시 동작 기준)
특정 캐시 동작(경로 패턴)에 따라 필요한 요청만 로그 수집 가능
- 예: /images/* 경로에 대해서만 로그 수집

#### 로그 필드 지정
로그에 포함할 필드들을 사용자 정의 가능
- 예: EdgeLocation, BytesSent, URI, StatusCode, UserAgent 등

### 사용 사례
| 시나리오 | 설명 |
|:---:|:---:|
| 실시간 성능 분석 | 응답 지연 구간 추적, 병목 분석 등 |
| 보안 대응 | 이상 요청 탐지, 특정 IP/경로 차단 자동화 |
| 비용 최적화 | 경로별 캐시 미스 추적, 콘텐츠 최적화 |
| 사용자 행동 분석 | 특정 콘텐츠 요청 패턴 실시간 분석 |

### 요약
| 항목 | 설명 |
|:---:|:---:|
| 실시간 로그 목적 | 성능 모니터링, 보안, 행동 분석 등 |
| 전송 대상 | Kinesis Data Stream (실시간), 이후 Lambda 또는 Firehose 연계 |
| 선택적 수집 | 샘플링 비율, 경로 패턴 지정 가능 |
| 후속 처리 | S3 저장, OpenSearch 분석, Lambda 알림 등 |

이 기능을 활용하면 CloudFront 배포 상태를 실시간으로 가시화하고 자동화된 대응 시스템을 구축할 수 있습니다.
