## Docker 및 AWS ECS/ECR/Fargate 핵심 정리

### 1. Docker 개요

*   **정의**: 애플리케이션을 컨테이너 단위로 패키징, 배포, 실행하는 오픈소스 플랫폼입니다. 환경에 구애받지 않고 일관된 실행을 보장합니다.
*   **주요 특징**:
    *   운영체제 독립성: 어떤 OS에서도 동일하게 실행됩니다.
    *   예측 가능한 실행: 환경 차이로 인한 문제를 방지합니다.
    *   빠른 배포/롤백: 이미지 재배포만으로 코드 변경을 반영합니다.
    *   마이크로서비스 지원: 서비스 단위별 독립 배포가 용이합니다.
    *   클라우드 이전 용이: 온프레미스 환경을 클라우드로 옮기기 좋습니다.
*   **실행 구조**:
    *   서버(EC2 등)에서 Docker Daemon(에이전트)이 실행됩니다.
    *   하나의 서버에서 여러 Docker 컨테이너(예: Java, Node.js, MySQL)를 동시에 실행할 수 있습니다.
    *   모든 컨테이너는 호스트 OS의 커널을 공유합니다.

### 2. Docker 이미지 & 리포지토리

*   **이미지 저장소**:
    *   `Docker Hub`: 공개 리포지토리 (기본 이미지 제공).
    *   `Amazon ECR`: AWS 전용 프라이빗/퍼블릭 이미지 저장소.
*   **이미지 생성 및 실행 흐름**:
    1.  `Dockerfile` 작성 (설정 스크립트).
    2.  `docker build` 명령어로 이미지 생성.
    3.  `docker push` 명령어로 리포지토리에 업로드.
    4.  `docker pull` 및 `docker run` 명령어로 컨테이너 실행.

### 3. Docker vs. 가상 머신 (VM)

| 항목        | Docker                        | 가상 머신 (VM)                   |
| :---------- | :---------------------------- | :------------------------------- |
| 커널 공유   | O (호스트 OS와 공유)          | X (독립된 게스트 OS)             |
| 성능        | 가볍고 빠름                   | 무겁고 느림                      |
| 보안 격리   | 낮음 (자원 공유)              | 높음 (자원 완전 분리)            |
| 리소스 사용 | 적음                          | 많음                             |
| 실행 단위   | 컨테이너                      | 가상 머신 (예: EC2 인스턴스)     |

### 4. AWS에서의 Docker 활용

*   `Amazon ECS`: AWS의 기본적인 Docker 컨테이너 실행 및 관리 플랫폼입니다.
*   `Amazon EKS`: Kubernetes 기반의 컨테이너 오케스트레이션 서비스입니다.
*   `AWS Fargate`: 서버리스 방식으로 컨테이너를 실행하는 엔진입니다 (ECS/EKS와 연동). 인프라 관리가 필요 없습니다.
*   `Amazon ECR`: 컨테이너 이미지를 저장하고 관리하는 서비스입니다.

### 5. ECS Service Auto Scaling (자동 확장)

*   **개념**: ECS 서비스 내 태스크(컨테이너) 수를 자동으로 조절하는 기능입니다.
*   **확장 기준 지표**:
    *   ECS 서비스의 평균 CPU 사용률
    *   ECS 서비스의 평균 메모리(RAM) 사용률
    *   ALB (Application Load Balancer) 타겟 그룹별 요청 수
*   **스케일링 정책**:
    *   `Target Tracking`: 특정 지표 값(예: CPU 70%)을 목표로 자동 조절합니다.
    *   `Step Scaling`: 지표 값 구간에 따라 단계적으로 확장/축소합니다.
    *   `Scheduled Scaling`: 미리 정해진 시간에 따라 확장/축소합니다.
*   **EC2 시작 유형에서의 확장**:
    *   ECS 서비스 레벨의 확장(태스크 수 증가)과 별개로, **백엔드 EC2 인스턴스 자체의 확장**도 필요할 수 있습니다.
    *   **방법 1: Auto Scaling Group (ASG)**: EC2 인스턴스의 CPU 사용률 등에 따라 ASG가 인스턴스 수를 조절합니다.
    *   **방법 2: ECS Cluster Capacity Provider (권장)**: ASG와 연동되어, 새 태스크를 실행할 용량(CPU, RAM)이 부족할 때 **자동으로 ASG를 확장**하여 EC2 인스턴스를 추가합니다. Fargate는 서버리스이므로 이 과정이 필요 없습니다.
*   **동작 예시**:
    1.  사용량 증가로 CPU 사용률 급증.
    2.  CloudWatch 지표가 임계값을 초과하여 CloudWatch 알람 발생.
    3.  알람이 ECS Auto Scaling 트리거.
    4.  ECS 서비스의 희망 태스크 수 증가 → 새 태스크 시작.
    5.  (EC2 시작 유형의 경우) Capacity Provider가 필요 시 EC2 인스턴스 추가.

### 6. ECS - 롤링 업데이트

*   **개념**: ECS 서비스 업데이트 시(예: v1 -> v2), 태스크 시작/중단 순서와 개수를 제어하는 방식입니다.
*   **주요 설정**:
    *   `최소 상태 퍼센트(Minimum healthy percent)`: 업데이트 중 유지해야 하는 최소 정상 태스크 비율 (기본값 100%). 이 비율 미만으로 태스크가 줄어들지 않습니다.
    *   `최대 퍼센트(Maximum percent)`: 업데이트 중 허용되는 최대 태스크 비율 (기본값 200%). 기존 태스크 + 새 태스크의 합이 이 비율을 넘지 않습니다.
*   **동작 방식 예시**:
    *   **최소 50%, 최대 100% (4개 태스크 시작)**: 기존 태스크 2개 중단 (50% 유지) → 새 태스크 2개 시작 (100% 도달) → 나머지 기존 태스크 2개 중단 (50% 유지) → 새 태스크 2개 시작 (100% 도달). **기존 용량 내에서 업데이트**.
    *   **최소 100%, 최대 150% (4개 태스크 시작)**: 새 태스크 2개 시작 (150% 도달) → 기존 태스크 2개 중단 (100% 유지) → 새 태스크 2개 시작 (150% 도달) → 나머지 기존 태스크 2개 중단 (100% 유지). **용량을 초과하며 업데이트**.

### 7. ECS 솔루션 아키텍처 예시

*   **EventBridge + ECS (S3 이벤트 트리거)**: S3 버킷에 객체 업로드 시 EventBridge가 이를 감지하고, Fargate에서 ECS 작업을 실행하여 객체 처리 후 결과를 DynamoDB 등에 저장하는 서버리스 아키텍처.
*   **EventBridge + ECS (스케줄 트리거)**: EventBridge 스케줄 규칙(예: 매시간)에 따라 Fargate에서 ECS 작업을 정기적으로 실행하여 배치 처리 등을 수행하는 서버리스 아키텍처.
*   **SQS + ECS**: SQS 큐로 메시지를 보내면, ECS 서비스가 메시지를 폴링하여 처리. ECS 서비스 오토스케일링과 연동하여 큐의 메시지 양에 따라 작업 수를 동적으로 조절 가능.
*   **EventBridge + ECS (작업 상태 변경 감지)**: ECS 클러스터 내 작업의 상태 변경(시작, 중지 등) 이벤트를 EventBridge로 감지하여 SNS 알림 발송 등의 후속 조치 수행 가능.

### 8. ECS 태스크 정의 (Task Definition) 심화

*   **개념**: ECS 서비스가 하나 이상의 Docker 컨테이너를 어떻게 실행할지 정의하는 JSON 형식의 명세서입니다.
*   **주요 구성 요소**:
    *   `이미지 이름`: 사용할 Docker 이미지 URI (Docker Hub, ECR 등).
    *   `포트 매핑`: 컨테이너 포트와 호스트 포트(EC2 유형)를 연결.
        *   **EC2 시작 유형 (ALB 사용 시)**: 컨테이너 포트만 지정하면 `동적 호스트 포트 매핑`이 사용되어 호스트 포트가 임의로 할당됩니다. ALB는 ECS 서비스와 연동하여 이 동적 포트를 자동으로 찾아 연결합니다. (ELB는 지원 안 함)
        *   **Fargate 시작 유형**: 각 태스크가 고유한 ENI(네트워크 인터페이스)와 프라이빗 IP를 가지므로 컨테이너 포트만 정의하면 됩니다.
    *   `CPU 및 메모리`: 컨테이너에 필요한 리소스 양.
    *   `환경 변수`:
        *   하드코딩: 태스크 정의에 직접 값을 입력.
        *   동적 참조: SSM Parameter Store 또는 Secrets Manager에 저장된 값을 참조하여 런타임 시 주입 (API 키, 비밀번호 등 민감 정보에 유용).
        *   파일 로드: S3 버킷에 저장된 환경 변수 파일을 통해 대량 로드.
    *   `IAM 역할`:
        *   **Task Role (작업 역할)**: 컨테이너 자체가 다른 AWS 서비스(S3, DynamoDB 등)에 접근할 수 있도록 부여하는 IAM 역할. **태스크 정의 수준에서 설정**됩니다.
        *   **Task Execution Role (작업 실행 역할)**: ECS 에이전트가 ECR에서 이미지를 가져오거나 CloudWatch에 로그를 보내는 등 ECS 관련 작업을 수행하기 위한 IAM 역할.
    *   `로깅 구성`: CloudWatch Logs 등으로 로그를 전송하는 설정.
    *   `볼륨 (데이터 공유)`: 동일 태스크 내 여러 컨테이너 간 데이터 공유 또는 데이터 영속성을 위해 사용.
        *   **Bind Mounts**: 호스트(EC2) 또는 임시 스토리지(Fargate)의 디렉토리를 컨테이너에 마운트. 사이드카 컨테이너(로깅, 모니터링 등)와 메인 컨테이너 간 데이터 공유에 주로 사용됩니다. Fargate에서는 20~200GiB의 임시 스토리지 제공.
        *   **EFS Mounts**: EFS 파일 시스템을 컨테이너에 마운트하여 영구적이고 공유된 스토리지 사용.

### 9. EC2 태스크 배치 전략 및 제한 (EC2 시작 유형 전용)

*   **개념**: EC2 시작 유형 사용 시, 새로운 태스크를 어떤 EC2 인스턴스에 배치하고, 스케일 인 시 어떤 태스크를 종료할지 결정하는 규칙입니다. Fargate는 AWS가 관리하므로 해당되지 않습니다.
*   **배치 프로세스**:
    1.  CPU/메모리/포트 요구사항을 만족하는 인스턴스 식별.
    2.  태스크 배치 제한 조건 확인.
    3.  태스크 배치 전략에 따라 최적의 인스턴스 선택 후 배치.
*   **태스크 배치 전략 (Strategies)**:
    *   `Binpack`: CPU 또는 메모리 사용률이 **가장 높은** 인스턴스에 우선 배치하여 사용 중인 인스턴스 수를 최소화 (비용 절감).
    *   `Random`: 무작위로 배치.
    *   `Spread`: 특정 속성(예: `instanceId`, `ecs:availability-zone`)을 기준으로 태스크를 **균등하게 분산** 배치 (고가용성 향상).
*   **태스크 배치 제한 (Constraints)**: 특정 조건을 만족하는 인스턴스에만 태스크를 배치하도록 강제.
    *   `distinctInstance`: 서비스 내 모든 태스크를 서로 다른 인스턴스에 배치.
    *   `memberOf`: 클러스터 쿼리 언어(CQL)를 사용하여 특정 조건(예: 인스턴스 타입이 't2')을 만족하는 인스턴스에만 배치.

### 10. Amazon ECR (Elastic Container Registry)

*   **개념**: Docker 컨테이너 이미지를 저장, 관리, 배포하는 완전 관리형 AWS 서비스입니다.
*   **주요 특징**:
    *   프라이빗/퍼블릭 리포지토리 제공.
    *   ECS, EKS, Fargate와 완벽하게 통합됩니다.
    *   백엔드에서 S3에 이미지를 안전하게 저장합니다.
    *   IAM을 통해 접근 제어 및 권한 관리.
    *   이미지 취약점 스캐닝 (Amazon Inspector 연동), 버전 관리, 수명 주기 정책 등 지원.
*   **CLI 사용법**:
    1.  `aws ecr get-login-password ... | docker login ...`: AWS CLI를 사용하여 임시 Docker 로그인 자격 증명을 얻고 로컬 Docker CLI를 인증합니다.
    2.  `docker pull <이미지_URI>`: ECR 리포지토리에서 이미지 가져오기.
    3.  `docker tag <로컬_이미지> <ECR_이미지_URI>`: 로컬 이미지를 ECR 리포지토리 형식에 맞게 태그 지정.
    4.  `docker push <ECR_이미지_URI>`: 태그된 이미지를 ECR 리포지토리로 푸시.
    *   **오류 발생 시**: IAM 권한 문제일 가능성이 높으므로 관련 정책 확인 필요.

### 11. ECS 컨테이너 인스턴스 생명주기 관리

*   **컨테이너 인스턴스 상태에 따른 등록 해제 동작**:
    *   **RUNNING 상태에서 종료 시**: 
        *   컨테이너 인스턴스가 클러스터에서 자동으로 제거됨
        *   별도의 수동 등록 해제 작업이 필요하지 않음
    *   **STOPPED 상태에서 종료 시**:
        *   컨테이너 인스턴스가 클러스터에서 자동으로 제거되지 않음
        *   Amazon ECS 콘솔이나 AWS CLI를 사용하여 수동으로 등록 해제 필요
        *   등록 취소된 컨테이너 인스턴스는 더 이상 ECS 클러스터의 리소스로 표시되지 않음

*   **주의사항**:
    *   STOPPED 상태의 인스턴스 등록 해제는 반드시 Amazon ECS 콘솔에서 수행해야 함 (Amazon EC2 콘솔이 아님)
    *   수동 등록 해제가 필요한 경우, 먼저 인스턴스를 종료한 후 등록을 취소하는 순서로 진행

### 12. ECS 클러스터 쿼리 언어 (Cluster Query Language)

* **개념**: 
    * ECS의 컨테이너 인스턴스(EC2 기반)들을 속성(attribute) 기반으로 그룹화하거나 필터링하는 데 사용되는 표현식 언어입니다.
    * Task 배치 제한(Placement Constraints)의 `memberOf` 타입과 함께 사용하여 특정 속성을 가진 인스턴스에만 작업을 배치하도록 제어할 수 있습니다.

* **주요 속성 예시**:
    * `ecs.availability-zone`: 가용 영역
    * `ecs.instance-type`: EC2 인스턴스 타입
    * `ecs.cpu-architecture`: CPU 아키텍처 (x86_64, arm64 등)
    * 사용자 정의 메타데이터 속성

* **문법 예시**:
    ```json
    // 특정 인스턴스 타입에만 배치
    "placementConstraints": [
      {
        "type": "memberOf",
        "expression": "attribute:ecs.instance-type == t3.medium"
      }
    ]

    // 특정 가용 영역에만 배치
    "placementConstraints": [
      {
        "type": "memberOf",
        "expression": "attribute:ecs.availability-zone in [us-west-2a, us-west-2b]"
      }
    ]

    // ARM64 아키텍처에만 배치
    "placementConstraints": [
      {
        "type": "memberOf",
        "expression": "attribute:ecs.cpu-architecture == arm64"
      }
    ]
    ```

* **관련 개념과의 차이점**:
    * `Task Group`: 단순히 관련 작업(Task)의 논리적 그룹화일 뿐, 인스턴스 속성 기반 그룹화와는 무관합니다.
    * `Placement Strategy`: spread/binpack/random 등 작업 분산 방식을 정의하는 규칙이며, 속성 기반 필터링과는 다른 개념입니다.
    * `Placement Constraint (distinctInstance)`: 같은 노드에 동일 서비스가 중복 실행되지 않도록 하는 제약 조건이며, 속성 기반 필터링과는 다릅니다.

* **활용 사례**:
    * 특정 하드웨어 요구사항(예: GPU)이 있는 작업을 해당 기능을 갖춘 인스턴스에만 배치
    * 비용 최적화를 위해 특정 인스턴스 타입에만 작업 배치
    * 고가용성을 위해 여러 가용 영역에 걸쳐 작업 분산
    * 특정 CPU 아키텍처(ARM/x86)에 최적화된 작업을 해당 아키텍처의 인스턴스에만 배치
