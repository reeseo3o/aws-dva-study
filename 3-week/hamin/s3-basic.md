# S3 개요

Amazon S3(Simple Storage Service)는 무한대로 확장 가능한 객체 스토리지 서비스로,
전 세계적으로 다양한 웹 애플리케이션, 미디어 호스팅, 백업 및 복구, 분석 등에 활용되고 있습니다.

S3는 AWS 서비스들 간에도 공통 스토리지 백본처럼 작동하며,
외부 웹사이트나 앱에서도 정적 자산 저장소 또는 소프트웨어 업데이트 배포용으로 활용됩니다.

## 주요 사용 사례
- 백업 및 재해 복구
- 정적 웹사이트 호스팅
- 하이브리드 클라우드 스토리지 확장 (온프레미스 + 클라우드)
- 대용량 미디어 파일 저장 및 스트리밍
- 소프트웨어 업데이트 배포
- 아카이빙: 예) 나스닥은 7년치 데이터를 S3 Glacier에 보관

## S3 구조 및 객체
S3에서는 데이터를 버킷(Bucket) 단위로 저장하며, 버킷 내의 파일 하나하나를 **객체(Object)**라고 부릅니다.

### 버킷 (Bucket)
S3에서 데이터를 저장할 수 있는 최상위 컨테이너입니다.  
계정에 귀속되며, 전 세계적으로 고유한 이름을 가지고 리전(Region) 단위로 생성되지만 이름은 고유합니다.

### 객체 (Object)
실제 저장되는 파일 단위입니다.  
객체는 다음과 같은 구성 요소로 이루어져 있습니다:

- Key: 객체의 고유 경로
- Body: 객체의 본문 데이터 (파일 자체)
- Metadata: 시스템 및 사용자 정의 메타데이터
- Tags: 키-값 형태의 태그 (최대 10개까지)

업로드 관련 사항:  
- 객체 최대 크기: 5TB  
- 대용량 파일(100MB 이상)의 안정적인 업로드를 위해 멀티파트 업로드를 사용합니다.

※ 콘솔에서는 디렉터리처럼 보이지만, 실제로는 객체 키를 슬래시(/)로 구분하여 경로처럼 표현하는 것뿐입니다.

## S3 보안
S3의 보안은 크게 사용자 기반 보안과 자원 기반 보안으로 나뉩니다.

### 1. 사용자 기반 보안 (IAM)
IAM 사용자, 그룹, 역할에 IAM 정책(Policy)을 적용하여  
어떤 사용자가 어떤 S3 리소스에 어떤 API를 호출할 수 있는지를 제어합니다.

### 2. 자원 기반 보안
- 버킷 정책 (Bucket Policy): 버킷에 접근 가능한 계정/사용자를 명시
- ACL (Access Control List): 객체/버킷에 대한 개별 권한 부여 (예전 방식, 현재는 거의 사용하지 않음)
- 퍼블릭 액세스 설정: 외부에서 접근 가능하게 하려면 별도 허용이 필요합니다

퍼블릭 액세스 설정: 외부에서 접근 가능하게 하려면 별도로 허용 필요

버킷 정책 예시
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:user/OtherUser"
  },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::example-bucket/*"
}

### 계정 간 접근 (Cross-Account Access)
다른 계정(A)이 우리 계정(B)의 S3 버킷에 접근하려면, 우리 쪽 버킷 정책에 해당 계정/역할의 ARN을 명시해줘야 합니다.

이 때 API 호출 주체는 IAM User 또는 Role일 수 있으며, AWS CLI나 SDK를 통해 프로그래밍적으로 S3 API를 호출하게 됩니다.

## 정적 웹사이트 호스팅
S3는 정적 웹사이트 호스팅 기능을 제공합니다.

HTML, CSS, JS 같은 파일을 S3에 업로드하고

정적 웹사이트 호스팅을 활성화하면

인터넷 사용자가 HTTP로 접근 가능

주의 사항
퍼블릭 액세스 허용 필요

웹사이트 URL은 S3 버킷이 속한 리전에 따라 달라짐

## 버전 관리
S3는 버킷 단위로 **객체 버전 관리(Versioning)**를 설정할 수 있습니다.

같은 Key(경로)로 객체를 업로드하면 덮어씌우는 것이 아니라 새 버전으로 저장됨

실수로 삭제하거나 덮어쓴 파일을 이전 버전으로 복원 가능

버킷 생성 이후, 명시적으로 버전 관리를 활성화해야 작동합니다


## 버킷 복제
1. 동일 리전 복제 (SRR: Same-Region Replication)
* 같은 리전 안에서 버킷 → 버킷 복제
* 보통 버전 관리, 데이터 보호용으로 사용

2. 교차 리전 복제 (CRR: Cross-Region Replication)
* 다른 리전에 있는 버킷으로 복제
* DR(재해 복구), 지연 최소화 목적

3. 계정 간 복제
* 소스 버킷과 대상 버킷이 다른 AWS 계정에 있는 경우
* 보통은 보안/데이터 이관용


### 복제 조건
복제가 되려면 몇 가지 조건이 충족되어야 합니다.:
1. 양쪽 버킷 모두 버전 관리(Versions) 활성화돼 있어야 함
2. 소스 버킷에 복제 규칙(Replication Rule) 설정해야 함
3. 복제를 수행할 IAM Role이 있어야 함 (S3가 스스로 데이터를 복제하려면 권한이 필요)

## S3 스토리지 클래스

S3는 다양한 사용 목적에 맞춰 여러 **스토리지 클래스**를 제공합니다.  
클래스마다 **비용, 내구성, 가용성, 복구 시간** 등이 다르므로  
데이터의 사용 패턴에 따라 적절한 클래스를 선택하는 것이 중요합니다.

| 스토리지 클래스              | 내구성            | 가용성   | 복원 시간       | 특징                                               |
|------------------------------|-------------------|----------|------------------|----------------------------------------------------|
  | **S3 Standard**              | 99.999999999%     | 99.99%   | 즉시             | 자주 사용하는 데이터를 위한 기본 클래스           |
| **S3 Intelligent-Tiering**   | 99.999999999%     | 99.9~99.99% | 즉시          | 자동 계층화 (자주/드물게 접근 자동 판단)          |
| **S3 Standard-IA**           | 99.999999999%     | 99.9%    | 즉시             | 가끔 접근, 하지만 빠른 복원이 필요한 데이터       |
| **S3 One Zone-IA**           | 99.999999999%     | 99.5%    | 즉시             | 저렴하지만 AZ 하나에만 저장됨 (단일 AZ)          |
| **S3 Glacier**               | 99.999999999%     | -        | 수분~수시간      | 장기 보관용, 저렴한 비용, 비정기적 복원           |
| **S3 Glacier Deep Archive**  | 99.999999999%     | -        | 수시간~12시간    | 최저 비용, 거의 접근하지 않는 데이터용            |

### 내구성 vs 가용성 차이
- **내구성(Durability)**: 데이터를 **잃지 않을 확률**  
  - 99.999999999%는 이론상 **1,000만 개 객체 중 1개 손실될 확률**
- **가용성(Availability)**: 데이터를 **요청했을 때 바로 읽을 수 있는 확률**  
  - 99.99%라면 1년 중 약 **52분 동안만 불가능할 수 있음**
